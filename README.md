# Меняйка (Tricky Exchanger)

Веб-сервис многостороннего бартера: пользователь выставляет товар и описывает, что хочет получить взамен; система ищет **циклические цепочки обмена** между несколькими участниками (2–5 человек), предлагает варианты, собирает отклики и проводит сделку через мягкую и жёсткую блокировку заявок.

Продакшен: [https://menyayka.tech](https://menyayka.tech)

## Описание проекта

**Меняйка** — платформа для обмена вещами без денег. В отличие от классического «один-к-одному», продукт умеет собирать **кольцевые обмены**: A отдаёт товар B, B — C, C — A (и длиннее, до 5 участников).

Ключевые пользовательские сценарии:

- регистрация / вход / восстановление пароля;
- каталог своих товаров (CRUD, фото, архивация);
- заявки на обмен (что отдаю + что хочу);
- просмотр найденных цепочек-кандидатов;
- отклик (vote), второй раунд подтверждений, заморозка сделки;
- быстрая замена участника при отказе;
- отслеживание отправки и получения товара.

Под капотом: PostgreSQL + **pgvector**, embeddings (TEI / stub), кластеризация похожих заявок, DFS-поиск циклов, статусы цепочек `CANDIDATE → PROPOSED → FROZEN → …`, soft/hard lock и дедлайны.

## Инструкция по запуску

### Требования

- Docker + Docker Compose
- Make (опционально; можно вызывать `docker compose` напрямую)

### Весь проект одной командой

```bash
cp .env.example .env   # на Apple Silicon добавь TEI_IMAGE=...cpu-arm64-latest (см. .env.example)
docker compose up -d --build
# или: make up
```

Поднимается **всё**: PostgreSQL + pgvector, миграции, MinIO, TEI, backend и frontend.

| Что | URL |
|-----|-----|
| UI (frontend) | http://localhost:3000 |
| API (backend) | http://localhost:8080 |
| MinIO | http://localhost:9000 |

Фронт отдаёт статику и проксирует `/api` → backend, `/s3` → MinIO (same-origin, пустой `VITE_API_BASE_URL`).

Остановка:

```bash
make down        # контейнеры + данные БД/MinIO; кэш TEI сохраняется
make down-all    # полный сброс, включая кэш модели
```

### Разработка фронта без Docker (опционально)

Если правишь UI с hot-reload:

```bash
docker compose up -d db migrate minio minio-init tei app
cd frontend && npm ci && npm run dev   # http://localhost:5173 → proxy на :8080
```

### Полезные команды

```bash
make logs            # логи backend + frontend
make test            # unit-тесты backend
make test-e2e        # E2E API (лёгкий compose без TEI)
make loadtest        # k6: register → item → list → login
```

Подробности: [`backend/README.md`](backend/README.md), [`frontend/README.md`](frontend/README.md).

### E2E и CI

```bash
make e2e-up          # docker-compose.e2e.yml (stub embeddings)
cd backend && BASE_URL=http://localhost:8080 go test -tags=e2e ./tests/e2e/ -v
make e2e-down
```

На PR и перед деплоем в GitHub Actions обязательно проходят unit-тесты, проверки фронта и **E2E**.

### Продакшен

Стек: `docker-compose.prod.yml` + Caddy + образы из GHCR.  
Автодеплой на VPS при пуше в `main` (см. вклад Цароева А. и workflow `.github/workflows/deploy.yml`).

## Особенности реализации

### Matching и цепочки

1. Заявка получает embeddings (offer + want) через TEI (или stub в тестах).
2. Похожие заявки группируются в **кластеры** (cosine + категорийный отсев + direction margin).
3. Между кластерами строится граф; **DFS** ищет простые циклы длины 2–5.
4. Найденные циклы сохраняются как `CANDIDATE`, дедуплицируются и скорятся.
5. Участники ставят **направленные votes**; при замыкании кольца цепочка → `PROPOSED` (мягкая блокировка, дедлайн ~24ч).
6. Второй раунд подтверждений → `FROZEN` (жёсткая блокировка товаров/заявок).
7. При отказе — откат или **быстрая замена** участника из того же кластера.
8. Дальше — отслеживание отправки/получения до завершения обмена.

### Инженерные решения

- identity пользователя **только из JWT**, не из тела запроса;
- единый формат ошибок API;
- миграции отдельным Compose-сервисом до старта `app`;
- фото товаров в MinIO, в API — публичный `imageUrl`;
- ленивое снятие просроченных soft-lock на действиях с цепочкой;
- E2E против реального HTTP API; нагрузка — k6-сценарий auth/item flow.

### CI/CD

- на **pull request**: backend unit, frontend typecheck/lint/test, **E2E**;
- на **push в `main`**: те же проверки + обязательный E2E → сборка образов в GHCR → SSH-деплой на VPS (migrate + `docker compose up`) → Caddy отдаёт `menyayka.tech`.

## Планы на финал

Направления доработки продукта к финальной сдаче:

- **Обработка плохих случаев при получении товаров (спор)** — сценарий `DISPUTE`, если товар не соответствует заявке или возник конфликт на этапе выдачи: фиксация спора, остановка цепочки и правила возврата.
- **Анонимизация и деанонимизация участников цепочки (backend)** — до подтверждения сделки участники видят друг друга обезличенно (псевдонимы / аватары); после нужного статуса цепочки backend раскрывает контакты только вовлечённым сторонам.
- **Бустинги (ИИ) для оценки рейтинга успеха цепочки** — модель/скоринг, который повышает или понижает оценку вероятности успешного обмена по качеству заявок, истории и согласованности категорий.
- **Процесс доставки товара** — полный пользовательский и серверный контур логистики: сдача → проверка → хранение → выдача, статусы отправки/получения и дедлайны.
- **Киллер-фича — быстрая замена** — если участник отказался на этапе `PROPOSED`, система предлагает кандидата из того же кластера без полного развала цепочки (механика уже заложена в продукте и усиливается к финалу).

## Предложение по безопасности обмена

Чтобы участник цепочки не отдал свою вещь и не остался без встречного товара, обмен проходит через **ПВЗ по модели группового хранения**.

После подтверждения цепочки каждый участник обязан передать свой товар в ПВЗ до установленного срока. При приёме товар проверяется на соответствие характеристикам заявки. До завершения проверки всех товаров вещи хранятся в ПВЗ и **не выдаются** новым владельцам.

Цепочка готова к выдаче только когда **все** участники сдали товары и **каждый** товар прошёл проверку. После этого все вещи одновременно становятся доступны получателям.

Если кто-то не передал товар вовремя или товар не соответствует заявке, цепочка отменяется. Уже принятые в ПВЗ товары возвращаются первоначальным владельцам. Так никто не теряет свою вещь, пока не подтверждено, что вся цепочка может быть завершена.
