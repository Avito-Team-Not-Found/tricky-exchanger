# AGENTS.md

Инструкции для агентов, работающих в этой директории (`frontend/`). Это фронтенд сервиса
многостороннего бартера Tricky Exchanger.

Перед изменением функциональности или экранов — сначала `PROJECT.md` (бизнес-требования, API,
модели данных), затем `DESIGN.md` (дизайн-токены, компоненты, спецификация экранов). Оба
документа зафиксированы окончательно: значения в них (цвета, брейкпоинты, лимиты полей,
эндпоинты) — источник истины, а не предложения на выбор.

## Принципы разработки

_Частично основано на инженерных принципах Avito Playbook ([development-principles.md](https://github.com/avito-tech/playbook/blob/master/development-principles.md))._

- Не усложняй сверх необходимого: реализация соответствует масштабу задачи, а не гипотетическим будущим требованиям. Три похожие строки — нормально, преждевременная абстракция — нет.
- Прежде чем писать своё решение, проверь, нет ли готового в стеке проекта (Ant Design, TanStack Query, утилиты `shared/`). Свой код — только когда готового решения действительно нет.
- Мёртвый код, неиспользуемые компоненты и закомментированные блоки удаляются сразу, а не остаются «на будущее» или «на всякий случай».
- У пропсов компонента и у хука — обдуманный, стабильный публичный интерфейс; внутреннюю реализацию можно менять свободно, пока контракт наружу не меняется.
- Изменение контракта API (`PROJECT.md` §4), дизайн-решения (`DESIGN.md`) или структуры проекта отражается в соответствующем `.md`-файле в том же PR, что и код — не отдельным заходом «потом».
- Изменение не считается готовым без теста или ручной проверки в браузере — прохождение typecheck и lint не заменяет проверку поведения.
- Найденный баг не остаётся молча в беклоге: по каждому — явное решение (чиним сейчас / берём в работу с конкретным сроком / закрываем как невалидный).
- UI и логика разделены: компонент — «глупый» рендер, вся логика (запросы, вычисления, обработчики)
  выносится в кастомный хук, который компонент вызывает для обогащения данными.
- Одна фича — один кастомный хук. Логика внутри него переиспользуется, а не копируется между
  компонентами; мутации (TanStack Query `useMutation` и обвязка вокруг них) не copy-paste'ятся —
  общая мутация выносится в хук и переиспользуется всеми вызывающими местами.
- Логика тестируется изолированно от DOM: pure-функции — обычным unit-тестом, хуки — через
  `renderHook`, без рендера компонента там, где в этом нет необходимости (см. «Тесты»).

## Стек

- React 19 + TypeScript, сборка — Vite.
- Ant Design 6 (UI-kit), тема переопределяется через `ConfigProvider` в `src/app/providers/ThemeProvider.tsx`.
- Redux Toolkit + react-redux — только для `user` (данные, токен) и `theme`. Всё остальное состояние — TanStack Query.
- TanStack Query — весь обмен данными с API, кеш и инвалидация.
- React Router — роутинг.
- Axios — HTTP-клиент.
- Vitest + React Testing Library — тесты.

Не добавляй альтернативные библиотеки для того, что уже покрыто стеком выше (другой
HTTP-клиент, другой стейт-менеджер, другой UI-kit) — стек зафиксирован в `PROJECT.md` §3.1.

## Структура (Feature-Sliced Design)

```
src/app/       — провайдеры, роутинг, стор, глобальные стили
src/pages/     — экраны
src/features/  — пользовательские сценарии (создание товара, создание запроса, выбор цепочки...)
src/entities/  — бизнес-сущности (товар, запрос, пользователь, цепочка)
src/shared/    — переиспользуемые UI-компоненты, API-клиент, утилиты, типы
```

Импорты идут только "вниз" по списку: `app → pages → features → entities → shared`. Слой не
может импортировать из вышестоящего слоя и не может импортировать напрямую из соседнего слоя
того же уровня в обход `shared`/`entities`. Это правило зашито в
`eslint.config.js` (`import-x/no-restricted-paths`) — при нарушении будет ошибка линта, а не
предупреждение.

Пути-алиасы (см. `tsconfig.app.json`): `@app/*`, `@pages/*`, `@features/*`, `@entities/*`,
`@shared/*`. Использовать их вместо относительных импортов через несколько уровней (`../../..`).

### `shared/`

`shared/` — только для по-настоящему переиспользуемого кода: форматтеры, хелперы, хуки, нужные
в 2+ фичах. Признак того, что функция не годится в `shared`: если её пришлось бы переписывать
для использования в чужом, не связанном с этим доменом проекте — значит, она знает про домен
(товары, обмены, цепочки) и её место в `entities`/`features`, а не в `shared`.

Антипаттерны:

- единый безымянный `utils.ts` без конкретной темы — разбивать на именные подфайлы
  (`formatDate.ts`, `formatCurrency.ts` и т.п.), а не копить всё в одном файле;
- заранее обобщать — писать «одну функцию на все случаи жизни» до того, как появился второй
  реальный вызывающий. Сначала пишется конкретная функция под конкретный кейс, обобщение
  (вынос в `shared`, добавление параметров) происходит по факту появления второго использования,
  а не заранее «на всякий случай».

### Состояние

Флаг-`useState` для отслеживания одного из нескольких взаимоисключающих состояний (загрузка/
успех/ошибка и т.п.) не используется — вместо набора булевых флагов пишется один
discriminated union тип, где в каждой ветке указаны только реально доступные в ней данные:

```ts
type State =
  | { status: 'initial' }
  | { status: 'loading' }
  | { status: 'success'; data: User }
  | { status: 'error'; message: string };
```

Такой тип не даёт по ошибке прочитать `data` в ветке `error` или `message` в ветке `success` —
применимость поля к ветке проверяется компилятором, а не по памяти.

## Команды


После любых изменений в `src/` перед тем как считать задачу выполненной — прогнать
`npm run typecheck`, `npm run lint` и `npm run test`. Форматирование (`npm run format`) — по
необходимости, но не должно расходиться с Prettier-конфигом.

## Стиль кода

- Точки с запятой обязательны, одинарные кавычки, `printWidth: 100`, trailing comma всегда — см.
  `.prettierrc`. Не переопределять локально.
- `message`, `notification` и `Modal` из пакета `antd` импортировать запрещено линтом —
  использовать `App.useApp()` (см. правило `no-restricted-imports` в `eslint.config.js`), иначе
  эти компоненты не подхватывают тему.
- Порядок импортов и группировка (builtin → alias-группы → относительные, с пустой строкой между
  группами и алфавитной сортировкой внутри) проверяется линтом (`import-x/order`) — не
  выравнивать импорты вручную в другом порядке.
- Компоненты — функциональные, без классовых компонентов.

## Комментарии в коде

- Только на русском языке.
- Комментарий пишется, только когда без него неочевидна причина решения (скрытое ограничение,
  обход бага, неочевидный порядок операций, нетривиальная бизнес-логика из `PROJECT.md`/`DESIGN.md`).
  Если по удалении комментария код остаётся понятным сам по себе — комментарий лишний, не пишется.
- Формат — одна строка `//` непосредственно над кодом, к которому относится. Без блоков `/** ... */`,
  без многострочных пояснений, без пустой строки между комментарием и кодом.
- Комментарий описывает **причину** («почему так»), а не **действие** («что делает код») — действие
  и так читается по именам переменных/функций.
- Не документировать очевидное, типы, сигнатуры и параметры — для этого есть TypeScript.
- Не писать комментарии-нарративы о процессе работы: «исправлено», «было так — стало так»,
  ссылки на тикеты/чаты/автора, следы правок. Комментарий описывает код, а не историю его изменений.

Плохо:

```ts
// увеличиваем retry на 1, потому что раньше было 0, а тестировщик попросил добавить
retry: 1,
```

Хорошо:

```ts
// сервер отдаёт мок-данные с редкими 502 при холодном старте — один повтор гасит их без задержки для юзера
retry: 1,
```

## Тема и дизайн-токены

- CSS-переменные темы объявлены в `src/app/styles/tokens.scss` и переключаются атрибутом
  `data-theme="light" | "dark"` на корневом элементе. Тема Ant Design синхронизирована с этими же
  значениями в `ThemeProvider.tsx` — оба места менять синхронно.
- Не хардкодить цвета/отступы/радиусы в компонентах — использовать токены из
  `tokens.scss` (`--color-*`, `--spacing-*`, `--radius-*`) или пропсы темы Ant. Значения токенов
  зафиксированы в `DESIGN.md` §1 — не подбирать новые оттенки по вкусу.
- Брейкпоинты: 375 / 768 / 1024px, одна адаптивная разметка на все три (см. `DESIGN.md` §1.7),
  не отдельные мобильная/десктопная вёрстки.
- Любое состояние (успех/ошибка/предупреждение/вероятность) всегда дублируется иконкой и/или
  текстом, не только цветом — это требование доступности из `DESIGN.md`, а не опция.

## API

- Базовый URL — `VITE_API_BASE_URL` (см. `src/shared/config/env.ts`); префикс `/api/v1`
  добавляется в API-клиенте (`src/shared/api`), не в каждом вызове по отдельности.
- JWT хранится в `localStorage` и добавляется в заголовок `Authorization: Bearer <token>` через
  Axios-интерцептор в `shared/api` — не проставлять заголовок вручную в каждом запросе. Выход —
  чисто клиентский (токен удаляется из `localStorage`), без обращения к серверу.
- Контракты эндпоинтов — `PROJECT.md` §4. Не придумывать новые поля/эндпоинты без сверки с этим
  разделом; если для фичи не хватает эндпоинта — сначала дополнить `PROJECT.md`, потом код.
- `src/shared/api/queryClient.ts` уже настроен (`retry: 1`, `staleTime: 60s`,
  `refetchOnWindowFocus: false`) — не создавать второй `QueryClient` рядом, использовать этот.

## Тесты

- Vitest + React Testing Library, окружение — jsdom (`vitest.setup.ts`).
- Обязательно покрывать тестами: утилиты, логику авторизации (защита маршрутов, работа с
  токеном), ключевые хуки работы с API. 100%-ное покрытие не требуется.
- Не мокать TanStack Query руками — оборачивать рендер в `QueryClientProvider` с отдельным
  тестовым `QueryClient` (`retry: false`, чтобы падающие запросы не ждали ретраев в тестах).
- Тесты пишутся сразу во время разработки нового функционала, не отдельным заходом «потом».
- Тест — для качества, не для метрики покрытия: набор тестов ради процента строк без проверки
  реального поведения не даёт ценности.
- Один тест проверяет одну конкретную вещь. Если в тесте несколько независимых утверждений
  про разное поведение — его нужно разделить на несколько тестов.
- От дешёвых к дорогим — писать тесты в таком порядке приоритета:
  1. **Unit — pure-функция.** Изолированный тест функции без React и без сети.
  2. **Unit — кастомный хук.** Проверяется через `renderHook`, без рендера компонента.
  3. **Integration — компонент + хук + API.** Рендерим фичу целиком, кликаем, ждём результат.
     Такой тест дороже — один на важный flow, не на каждый компонент.

## Коммиты

- Сообщение коммита — на английском языке, по [Conventional Commits](https://www.conventionalcommits.org/)
  (`type(scope): summary`, например `feat(products): add photo upload field`,
  `fix(auth): redirect to login on expired token`).
- Одна строка — только заголовок, без тела и без bullet-списков после него.
- Одно логическое изменение — один коммит: не сваливать в один коммит несвязанные правки
  (например, новую фичу и рефактор соседнего модуля, или фронтенд- и бэкенд-часть задачи).
  Если изменение затрагивает несколько независимых аспектов — разбивать на последовательность
  коммитов, а не описывать всё одной строкой через «и»/`,`.

## Чего не делать

- Не реализовывать подтверждение мягкой блокировки (`freeze-votes`), замену участника
  (`replacement-candidates`) и экраны трекинга доставки — они в контракте (`PROJECT.md` §4.6–4.7),
  но в текущем MVP не реализованы. Отклик (`accept`/`decline`) и выбор готовой цепочки
  (`select` → `PROPOSED`) — реализованы, см. `PROJECT.md` §4.4–4.5.
- Не добавлять чат, историю обменов, рейтинги/отзывы, email/push-уведомления — вне рамок MVP
  (`PROJECT.md` §1.3).
- Не вводить сторонние UI-библиотеки поверх Ant Design для тех же задач (модалки, тосты, формы).
