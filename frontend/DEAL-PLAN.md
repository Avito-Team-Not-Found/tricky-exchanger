# План: экраны сделки — отправка и получение товаров (макеты 4.9)

Ветка: `feat/final-delivery-stage` (от `d50ee94 feat(chains): track exchange fulfillment`).
Дата: 2026-08-10.

Задача: реализовать группу экранов **4.9 «Сделка»** из Penpot (страница «Мобила») — отправку
товара, ожидание доставки, получение — вместе с сопутствующими модальными окнами и точками
входа на экранах 4.6/4.7.

Особенность MVP: физического ПВЗ нет. Отправку и получение формально должна подтверждать
интеграция с Авито; вместо неё на экранах стоят **кнопки-заглушки** («Я отправил товар»,
«Я забрал товар»), которые дёргают те же ручки. Фото товара и адрес ПВЗ бэкенд не хранит —
имитируем на фронте (§4).

## 2. Что уже есть на бэкенде (проверено по коду)

### 2.1. Деанонимизация участников — отложена

Обсуждалась идея снимать анонимность с `FROZEN` (имя + аватар вместо животного). **Решено
не делать** (2026-08-10): на всех экранах, включая 4.9, участники остаются псевдонимами-
животными по позиции, правило `DESIGN.md` §2.9 не меняется.

Для протокола, если вернёмся: имён в API цепочек нет вообще — `chainParticipantResponse`
отдаёт только `isCurrentUser`, ФИО лежит в `users.full_name` (`migrations/000002`), а
`repository.loadParticipants` таблицу `users` не джойнит; аватара в БД нет ни у кого. То есть
это правка бэкенда (JOIN + новое поле, отдаваемое только на `FROZEN/IN_PROGRESS/COMPLETED`
и уже сокращённое до «Алексей П.»), а не фронта.

### 2.2. Ручки отправки и получения

Обе ручки существуют и работают; фронт их не вызывает вообще.

| Метод | Эндпоинт                              | Авторизация | Тело                          |
| ----- | ------------------------------------- | ----------- | ----------------------------- |
| POST  | `/api/v1/integrations/avito/handoffs` | **нет**     | `{"chainId":1,"requestId":2}` |
| POST  | `/api/v1/chains/{chainId}/receipt`    | Bearer      | `{"requestId":2}`             |

Ответ обеих: `{"chainId":1,"requestId":2,"status":"IN_PROGRESS"}` (`status` — новый статус
цепочки). Опорные точки: `backend/internal/core/router/router.go:88,97`,
`backend/internal/handler/chain/handler.go` (`Handoff`, `ConfirmReceipt`),
`backend/internal/service/chain/service.go:567,608`.

**Семантика `requestId` — ключевая деталь:**

- `handoffs` — `requestId` **своей** заявки (`chain.currentRequestId`): «я отдал свой товар».
  Заявка `LOCKED → IN_PROGRESS`, цепочка `FROZEN → IN_PROGRESS`.
- `receipt` — `requestId` заявки **звена-источника**, то есть участника на
  `chain.receivesFromPosition` (`receivesItem(chain)[0].requestId`): «я забрал товар,
  который отправлял он». Заявка источника `IN_PROGRESS → DONE`. Когда все заявки цепочки
  `DONE`, цепочка `COMPLETED` (`repository.AllChainRequestsDone`).
- Получение возможно только после отправки: если заявка источника ещё `LOCKED`, ответ
  `409 «передача товара ещё не подтверждена»`.

**Статус заявки участника — единственный источник состояния экрана.** Бэкенд уже отдаёт его
в `GET /chains/{id}` (`chainParticipantResponse.requestStatus`, `handler.go`), но **во фронтовой
модели `ChainParticipant` поля нет** — добавить (§5.1). Для несобранных цепочек
(`status <> CANDIDATE`) на каждую позицию приходит ровно один участник
(`repository.loadParticipants`: `member.request_id = cp.request_id`), поэтому пул кандидатов на
экранах сделки не мешает.

Расшифровка `requestStatus` участника P:

| Статус        | Смысл                                                      |
| ------------- | ---------------------------------------------------------- |
| `LOCKED`      | закреплён в цепочке, товар **не отправлен**                |
| `IN_PROGRESS` | P **отправил** свой товар (в нашей имитации = «в ПВЗ»)     |
| `DONE`        | получатель (позиция P−1) **подтвердил получение** товара P |

Ещё пригодится: `chain.freezeDeadlineAt` — при заморозке ставится `now + 24h`
(`freeze_service.go:11,43`). Это реальный дедлайн для таймера «Осталось N ч M мин на отправку»
(в макете нарисовано 47:58 — у нас TTL 24 ч, показываем фактическое значение).

Коды ошибок: `403` «только получатель товара может подтвердить его получение» · `404` цепочка
не найдена · `409` «цепочка не готова к передаче товаров» / «передача товара ещё не
подтверждена» · `422` «заявка не является закреплённым товаром этой цепочки».

## 3. Раунд 2: согласие всех участников и переход в `FROZEN` (Этап 0)

Экраны 4.9 живут на статусах `FROZEN` / `IN_PROGRESS` / `COMPLETED`. Перевод
`PROPOSED → FROZEN` делает бэкенд, когда **каждый** участник вызвал
`POST /chains/{id}/confirm` (`service.go:447-465`), — и этот шаг доводится до конца
из интерфейса, отдельного «согласия» вне фронта не требуется.

Сейчас кода раунда 2 на фронте нет: `useChainVote` доводит цепочку только до `PROPOSED`
(тост «Цепочка собрана»), вызовов `confirm/think/decline` в `src/` нет ни одного. Значит
Этап 0 — **обязательная часть этой задачи**, а не опция: без него цепочка не выходит из
`PROPOSED` и экраны сделки не открываются.

Макеты для него уже нарисованы: `4.6 Модальное окно — Готовность к сделке`,
`4.6 — Пока вы думаете`, `4.7 — Требуются действия`, `4.7 — Я согласился`.

Ручки готовы: `POST /chains/{id}/confirm` (→ `{chainId,status}`), `POST /chains/{id}/think`,
`POST /chains/{id}/decline` (→ `{chainId,status,replacementAvailable}`).

Объём Этапа 0 (замена участника, `replacements`, — **вне** плана):

- `entities/chain/api.ts`: `confirmChain`, `thinkChain`, `declineChain`;
- `features/chains/model/useChainRound2.ts` — одна мутация на три действия, инвалидация
  `['chains']` / `['exchange-options']`, тост «Вы подтвердили участие» / «Отложено» / «Вы вышли
  из цепочки», разбор `409`;
- модалка `DealReadyModal` («Все участники найдены / Это действие заблокирует другие цепочки /
  Приступаем к сделке?» → «Да» `primary` / «Я подумаю» `secondary` / «Нет» `text` `danger`);
  «Я подумаю» открывает вторую модалку «Вы уверены? Пока вы думаете, ваше место в цепочке могут
  занять другие участники» (⏳, «Да» / «Вернуться»);
- CTA на 4.7 и в карточке 4.6 — см. §7.

## 4. Что имитируем на фронте (бэкенда нет)

Всё, что ниже, — клиентская имитация; в коде помечается комментарием
`// имитация: на бэкенде этого нет (DEAL-PLAN.md §4)`, чтобы потом было что искать.

### 4.1. Адрес ПВЗ

- Хранилище: `localStorage`, ключ `deal:pickup:<chainId>`, через `shared/lib/storage.ts`
  (там уже есть типизированные обёртки — расширить тем же способом, не писать свой `JSON.parse`).
- Значение по умолчанию — первый из зашитого списка 5 адресов
  (`features/deal/model/pickupPoints.ts`).
- Кнопка «Изменить» открывает модалку: `Select` со списком + вариант «Другой адрес» с `Input`.
  Пустой адрес не сохраняется.
- Подпись под карточкой — из макета дословно: «Это пункт назначения — куда должен прийти ваш
  товар для получателя. Отправить его вы можете через любой удобный ближайший пункт приёма».

### 4.2. Фото товара перед отправкой

- `<input type="file" accept="image/*">` (в UI — блок-заглушка 📷 «Прикрепить фото»,
  `bg-card`, radius-md).
- Файл ужимается через `canvas` до 512px по большей стороне, `toDataURL('image/jpeg', 0.7)`,
  кладётся в `localStorage` по ключу `deal:photo:<chainId>:<requestId>`. Квота может кончиться —
  запись в `try/catch`, при ошибке фото остаётся только в состоянии страницы, кнопка отправки
  всё равно разблокируется (тост не показываем: пользователю это ничего не даёт).
- Поле обязательное (в макете `*`): без фото кнопка «Я отправил товар» `disabled`, под ней
  подсказка «Прикрепите фото товара перед отправкой».
- Превью с кнопкой «Заменить фото» / «Удалить».
- **Не** отправляем в `POST /items/{id}/image`: это фото упаковки, а та ручка перезапишет
  фото товара в каталоге.

### 4.3. Трекинг доставки (модалка)

Событий и времени у нас нет. Показываем фиксированный список этапов, «пройденность» считаем
по `requestStatus` участника, **без дат**:

| `requestStatus` | Пройдены                                                                     |
| --------------- | ---------------------------------------------------------------------------- |
| `LOCKED`        | ничего (все точки серые, подпись «Отправитель ещё не принёс товар»)          |
| `IN_PROGRESS`   | «Принято в отделении», «В сортировочном центре», «Доставлено в пункт выдачи» |
| `DONE`          | те же + «Получено»                                                           |

Последний пройденный этап — жирный, точка `accent-primary`; пройденные — `status-success`;
непройденные — серые. Ровно поэтому в списке нет времени: подставлять правдоподобные, но
выдуманные даты в интерфейс, который выглядит как реальный трекинг, — хуже, чем их не иметь.

### 4.4. Спор

Ручки нет. «Открыть спор» → модалка-подтверждение → модалка успеха «Жалоба отправлена»
(🛠, текст из макета) → флаг в `localStorage` `deal:dispute:<chainId>`, чтобы после перезагрузки
вместо ссылки показывалась строка «Жалоба на рассмотрении». Никаких сетевых запросов.

### 4.5. Кнопки-заглушки вместо ПВЗ

Две кнопки, которые в проде дёргала бы интеграция:

- «Я отправил товар» → `POST /integrations/avito/handoffs`;
- «Я забрал товар» → `POST /chains/{id}/receipt`.

Оформление: обычная `primary large block` кнопка + под ней Caption `text-secondary`
«Обычно это подтверждает пункт выдачи — в демо подтверждаете вы». Обе операции необратимы,
поэтому каждая идёт через `Modal.confirm` (`DESIGN.md` §2.11).

## 5. Данные и модель состояния

### 5.1. `entities/chain`

- `model.ts`:
  - в `ChainParticipant` добавить `requestStatus: RequestStatus` (тип из
    `@entities/exchangeRequest`; импорт entities→entities линтом разрешён);
  - `export interface FulfillmentResult { chainId: number; requestId: number; status: ChainStatus }`;
  - `sourceParticipant(chain)` — участник на `receivesFromPosition` для собранной цепочки
    (обёртка над существующим `receivesItem`, возвращающая единственного или `null`);
  - `dealState(chain): DealState` — чистая функция, discriminated union (`AGENTS.md`, §Состояние):

    ```ts
    type DealState =
      | { status: 'waiting-confirmations' } // PROPOSED
      | { status: 'ship'; deadlineAt: string | null } // FROZEN, моя заявка LOCKED
      | { status: 'shipped-waiting'; shipped: number; total: number } // я отправил, отправили не все
      | { status: 'in-transit'; shipped: number; total: number } // все отправили, я ещё не забрал
      | { status: 'received-waiting' } // я забрал, цепочка ещё идёт
      | { status: 'completed' } // COMPLETED
      | { status: 'unavailable' }; // CANDIDATE/BROKEN — экран недоступен
    ```

    Правила: «отправил» = `requestStatus !== 'LOCKED'`; «я забрал» = у участника-источника
    `requestStatus === 'DONE'`; `total = chain.length`.
    В `in-transit` действие «Я забрал товар» доступно, только если источник `IN_PROGRESS`.
- `api.ts`: `confirmHandoff(chainId, requestId)`, `confirmReceipt(chainId, requestId)` →
  `FulfillmentResult`.

### 5.2. `features/deal`

- `useDealFulfillment(chainId)` — **одна** мутация на оба действия (`kind: 'handoff' | 'receipt'`),
  как `useChainVote` (`AGENTS.md`: мутации не копипастятся):
  - `onSuccess`: инвалидация `['chains']`, `['exchange-options']`, `['exchange-requests']`
    (статусы заявок меняются, «Мои запросы» показывают их тегом); для `receipt` — открыть
    модалку «Получение подтверждено», для `handoff` — тост «Отправка подтверждена»;
    при `status === 'COMPLETED'` — тост «Обмен завершён»;
  - `onError`: карта сообщений `403/404/409/422` (§2) + инвалидация кэша.
- `useDealPhoto(chainId, requestId)` и `usePickupPoint(chainId)` — обёртки над `localStorage`
  из §4.1–4.2.

## 6. Экраны 4.9 — спецификация

Общее: шапка `ChainPageHeader` (переиспользуем) с заголовком «Сделка» и «Назад» на
`/chains/:chainId`; нижняя кнопка `secondary large block` «Посмотреть детали цепочки» →
`/chains/:chainId`; глобального таб-бара нет (`DESIGN.md` §2.12, как у 4.7/4.8). Цвета —
токенами: `#FAAD14` warning, `#52C41A` success, `#1677FF` accent, `#F7F9FC` bg-card,
плашки — заливка тона 12%, radius-md.

**A. `ship` — «Отправка товара»**

Таймер (`warning`, ⏱, «Осталось N ч M мин на отправку», из `freezeDeadlineAt`; при истёкшем —
«Срок отправки истёк», тон `error`) → блок «Вы отправляете: [мой товар] → [получаемый]»
(`DealItemSwap`, миниатюры 28×28) → зелёная строка «🔒 Мы сохраним ваш товар ›» → «Что нужно
сделать» (3 шага из макета, название товара подставляется) → карточка ПВЗ с «Изменить» и
пояснением → поле фото (обязательное) → **кнопка-заглушка «Я отправил товар»** → «Посмотреть
детали цепочки».

**B. `shipped-waiting` — «Ждём остальных»**

🚚, заголовок «Вы отправили товар», текст «Ждём, пока остальные участники принесут свои товары».
Плашка прогресса «Отправлено N из M». Ссылка «Статусы отправки» → `/deal/shipments`.
Зелёная строка «🔒 Сделка защищена ›» (текст модалки — вариант «Товары под защитой»).

**C. `in-transit` — «Товары в пути» / «Все товары доставлены»**

Все отправили → по макету «Все товары доставлены» (зелёный блок ✅, «Ваш товар уже в пункте
выдачи. Заберите его в удобное время»), карточка ПВЗ, блок «Вы получите: A → B»,
строка «Проблемы с товаром? **Открыть спор**», **кнопка-заглушка «Я забрал товар»**.
Если отправили не все (у меня уже отправлено, но кто-то `LOCKED`) — вариант «Товары в пути»
(🚚, «Все участники отправили товары» / «Ждём остальных»), секция «Статус доставки» с плашкой
«N из M доставлено» и строками товаров (миниатюра, название, пилюля «В пути» `accent` / «Доставлено»
`success`, `›` → `DealTrackingModal`), кнопка «Я забрал товар» `disabled` с подписью
«Дождитесь, пока отправитель принесёт товар».

**D. `received-waiting`** — 🎉 «Вы забрали товар», «Обмен завершится, когда все участники

**H. Статусы отправки / получения** (`/deal/shipments`, `/deal/receipts`)

## 11. Риски

- **Двойное подтверждение отправки.** `handoffs` идемпотентен по факту (повторный вызов не
  меняет уже `IN_PROGRESS`-заявку), но ручка не требует авторизации и принимает любой
  `chainId/requestId` — в UI кнопку показываем только своему участнику и только в состоянии
  `ship`.
- **Гонка статусов.** Пока экран открыт, другой участник может всё отправить/забрать. Ставим
  `refetchInterval` 15 с на `useChain` только на странице сделки и инвалидируем кэш после
  каждой мутации; `409` не считаем ошибкой пользователя — тост + перезагрузка данных.
- **Квота `localStorage`** на фото — см. §4.2.
- **Отказ участника (`decline`) на этапе PROPOSED** удаляет строку голоса и не оставляет следа
  (известная особенность, memory `decline-leaves-no-trace-in-chain`) — на экранах сделки это
  не проявляется, но при тестировании Этапа 0 сбивает с толку.
