# Техническое задание (ТЗ) на разработку MVP сервиса многостороннего бартера

---

## 1. Введение

### 1.1. Цель проекта

Создать MVP веб‑приложения для многостороннего обмена (бартера) вещами. Пользователь может добавить свои товары, создать запрос на обмен, увидеть возможные цепочки обмена и выбрать подходящую. Сервис делает схему обмена прозрачной, поддерживает доверие участников и позволяет управлять процессом.

### 1.2. Бизнес-задача

- Помочь пользователю обменять ненужную вещь на желаемую.
- Объединять пользователей в цепочки, где каждый отдаёт одну вещь и получает другую.
- Обеспечить понятный и безопасный сценарий обмена.

### 1.3. Ограничения MVP

- Цепочка проходит согласованный жизненный цикл подтверждения между участниками (см. §4.4–4.8): кандидатная цепочка (`CANDIDATE`) → отклики участников «принять/отклонить» → собранная цепочка (`PROPOSED`) → повторное подтверждение участия до дедлайна (`confirm`/`think`/`decline`, §4.6) → заморозка (`FROZEN`); дальше — отправка и получение товаров (`handoffs`/`receipt`, §4.7) до `COMPLETED`; при отказе или истечении дедлайна доступна замена выбывшего участника (`replacement-candidates`, §4.8).
- Вне рамок MVP: чат между участниками, история обменов, рейтинги и отзывы, доставка уведомлений по email/push (in-app уведомления — часть контракта, см. §4.9, §2.9).

## 2. Функциональные требования (экраны и сценарии)

### 2.1. Авторизация

**Экран входа** (`/login`)

- Поля: Email, Пароль.
- Кнопка «Войти».
- При успешном входе – редирект на главный экран (список товаров).

**Экран регистрации** (`/register`)

- Поля: Имя, Email, Пароль (минимум 8 символов), Подтверждение пароля.
- Кнопка «Зарегистрироваться».
- После регистрации – автоматический вход и редирект на главный.
- Переключение между входом и регистрацией — таб-переключателем над формой.

**Защита маршрутов**: все страницы, кроме `/login` и `/register`, доступны только авторизованным пользователям. Неавторизованный пользователь перенаправляется на `/login`.

### 2.2. Главный экран – список товаров пользователя

**Экран** `/products`

- Отображает все товары текущего пользователя (без архивных).
- Каждая карточка товара содержит: фото (превью), название, категорию (строкой под названием, скрыта у товаров без категории), статус (`активен`, `недоступен`, `в архиве`).
- Иконки редактирования и удаления (доступны по наведению / долгому нажатию).
- Кнопка «+» (добавить товар) в хедере или плавающая кнопка.
- Пустое состояние: «У вас пока нет товаров. Нажмите «+», чтобы добавить».

### 2.3. Создание / редактирование товара

**Экран создания** (`/products/new`) и **редактирования** (`/products/:id/edit`)

- Заголовок: «Новый товар» или «Редактирование товара».
- Кнопка «Назад» → возврат на список товаров.
- Поля:
  - Фото (один загрузчик с превью и возможностью замены/удаления, обязательное) – в мобильном макете один снимок, контракт допускает несколько. Фото грузится отдельной ручкой `POST /items/{itemId}/image` (multipart, поле `image`) после создания/вместе с правкой товара.
  - Название (`title`, обязательное, до 100 символов).
  - Описание (`description`, обязательное, до 500 символов).
  - Категория (`category`, **обязательная**) — выбор из фиксированного списка `@shared/config/categories`: «Личные вещи», «Для дома и дачи», «Запчасти и аксессуары», «Электроника». Ручки-справочника у бэкенда нет, категория хранится текстом в `items.category`, поэтому список опций живёт константой на фронте (таблица `categories` из сида осиротела после миграций `000010`/`000012` и наружу не отдаётся). Свободный ввод запрещён: кластеризация сравнивает категорию точным строковым равенством (`FindSimilarOffers` → `backend/internal/repository/search/top_k.go`), и опечатка развела бы взаимозаменяемые заявки по разным пулам кандидатов. **Категория не ограничивает, с кем пользователь меняется** — партнёр по обмену стоит в соседнем звене кольца и может быть любой категории; равенство категорий требуется только внутри одного звена. У товаров, созданных до перехода на текстовую категорию, `category` пустая — при первом же редактировании такого товара форма потребует выбрать категорию, и заявки с ним переедут в другой кластер. Поля `color`/`material`/`attributes` из ранних версий убраны — колонок в БД нет (SCRUM-50 §6.1).
- `embedding` товара frontend не передаёт и не показывает — backend вычисляет его сам.
- Кнопка «Сохранить» – активна только при заполнении всех обязательных полей.
- После сохранения – тост об успехе и редирект на `/products`.

### 2.4. Создание запроса на обмен

**Экран создания запроса** (`/exchange-requests/new`)

- Заголовок: «Новый запрос», кнопка «Назад».
- Блок «Что вы отдаёте?»:
  - Если у пользователя есть товары – отображается список его товаров с возможностью выбора (радио-кнопка или карточки с выбором).
  - Если товаров нет – показывается кнопка «Создать новый товар», которая открывает экран создания товара (после сохранения автоматически возвращает в форму запроса с выбором созданного товара).
- Блок «Что вы хотите получить?»:
  - Категория желаемого (`wantedCategory`, **обязательная**) — тот же справочник, что и у товара (`@shared/config/categories`). В подборе не участвует: бэкенд строит эмбеддинг желаемого только по `wantedDescription`.
  - Поле «Что вы хотите получить» (`wantedDescription`, обязательное, свободный текст, до 500 символов — заменяет прежние отдельные поля «название» + «описание» желаемого).
- Кнопка «Создать запрос» – активна при выборе отдаваемого товара, выбранной категории желаемого и заполненном тексте желаемого; повторная отправка при активном запросе недопустима (кнопка блокируется на время сабмита).
- После создания фронт показывает результат: заявка создана. Матчинг на бэкенде — заглушка (SCRUM-50 §5), поэтому заявка остаётся в поиске (`ACTIVE`), а раздел «Варианты обмена» показывает заглушку (см. §2.6).
- Если у пользователя нет товаров — вместо выбора отдаваемого товара показывается кнопка «Создать новый товар» (ведёт на `/products/new?returnTo=request`); после сохранения товара пользователь возвращается в форму запроса с выбором созданного товара.

**Экран редактирования запроса** (`/exchange-requests/:requestId/edit`)

- Те же поля, что при создании (кроме выбора отдаваемого товара — он фиксирован).
- Живая заявка (`ACTIVE`/`IN_PROPOSAL`) редактируется: `PUT` с полным телом (`offeredItemId`, `wantedDescription`, `wantedCategory`, `version`) пересчитывает локальное окружение и запускает matching заново. Оптимистичная блокировка: при расхождении `version` сервер отвечает `409`, фронт инвалидирует кеш и предлагает обновить страницу.
- **`LOCKED`-заявка визуально защищена от обычного редактирования**: форма отображается в read-only, сверху баннер «Заявка заблокирована и защищена от редактирования», кнопка сохранения недоступна. `DONE`/`IN_PROGRESS` тоже не редактируются.

### 2.5. Мои запросы

**Экран** `/exchange-requests`

- Заголовок: «Мои запросы», кнопка «+» для создания нового.
- Список запросов в виде карточек:
  - Отдаваемый товар (название; фото не показывается — бэкенд не отдаёт снимок товара, см. §4.3) → желаемый товар (название).
  - Статус (тег): `Активен`, `В процессе`, `Зарезервирован`, `Завершён`, `Выполняется` (см. §4.3).
  - Тап по карточке → экран «Варианты обмена» (§2.6); редактирование запроса — кнопкой «Изменить запрос» в сводке этого экрана. Удаление живой заявки (soft-delete → `REMOVED`, из списка она исчезает) доступно на экране редактирования (§2.4), а не из списка.
- Пустое состояние: «У вас нет запросов. Создайте новый».

### 2.6. Просмотр запроса, список цепочек и их согласование

> **Статус раздела:** цепочки ходят в реальный API — варианты обмена
> (`GET /exchange-offers/{id}/exchange-options`), направленный отклик
> (`PUT/DELETE /chains/{id}/votes`). Флаг `VITE_FEATURE_CHAINS` снят. Контракт описан ниже (§4.4–4.7).

**Экран** `/exchange-requests/:requestId`

- Заголовок: «Варианты обмена», кнопка «Назад».
- Компактный блок с информацией о запросе: «Отдаёте: [товар]» / «Получаете: [желаемый]».
- Список вариантов обмена (`GET /exchange-offers/{requestId}/exchange-options`, статус `CANDIDATE`), отсортированных по убыванию `score`. Каждый вариант — конкретная заявка кандидата следующего звена (`receiveOptions`), для него показывается отдельная карточка.
- **Карточка варианта** содержит:
  - Фото, название и «что хочет взамен» получаемого товара.
  - Длину цепочки из `length` ответа (например, «3 участника») — не из размера пула кандидатов.
  - `score` как индикатор вероятности успеха (цветовой индикатор + процент, `score * 100`); у собранной цепочки (`PROPOSED` и дальше) место бейджа занимает пилюля «Цепочка собрана».
  - Действие зависит от статуса цепочки (SOFT-LOCK §5.1–5.5):
    - `CANDIDATE` — «Откликнуться» (если у варианта нет отклика) или «Отозвать отклик» (по `vote`, через Modal-подтверждение) — `PUT`/`DELETE /chains/{chainId}/votes`;
    - `PROPOSED` — рамка `status-success` и `primary` «Требуются действия»: модалка «Готовность к сделке» → «Да» подтверждает участие (`POST /chains/{chainId}/confirm`), «Я подумаю» откладывает решение голосом `thinking` (`POST /chains/{chainId}/think`), «Отказ» ведёт в подтверждение отказа → `POST /chains/{chainId}/decline` (второй раунд, §4.6). Если мой голос уже `thinking` — вместо кнопки предупреждение «⚠ Примите решение как можно скорее!» и inline-кнопки «Да» (подтверждение без модалки) / «Нет»; если `approved` — статусная пилюля «Вы подтвердили · ждём остальных»;
    - `FROZEN` — рамка `status-success` и `primary` «Требуется действие» (пора отправлять свой товар, ведёт на `/chains/:chainId/deal`, экран сделки — §4.7) и бейдж «M/M согласий»;
    - `IN_PROGRESS` — зелёная кнопка «Перейти к сделке» (тот же адрес) и бейдж «M/M согласий»;
    - `COMPLETED` — та же зелёная кнопка «Перейти к сделке» (на завершённой цепочке жёсткой блокировки уже нет, но сделку открыть нужно — `hasDeal`, DEAL-PLAN §5.1).
  - Когда одна из цепочек запроса замкнулась (`PROPOSED`, требует подтверждения) или заморожена — остальные карточки приглушены и недоступны; доступными остаются только собранные и замороженные цепочки. Когда сделка по одной из цепочек уже заморожена — дополнительно над списком баннер «Сделка по одной из цепочек уже согласована. Остальные варианты недоступны.» и кнопка правки запроса `disabled`.
  - Второй раунд на карточке: бейдж «N/M согласий» (пилюля сплошной заливки accent, белый текст). На `FROZEN` — всегда «M/M» (все подтвердили). На `PROPOSED` — `N` считается из `participants[].vote` детали цепочки (`GET /chains/{id}`): `exchange-options` счётчик не отдаёт, поэтому для PROPOSED-цепочек экран дополнительно подтягивает их детали. Из той же детали берётся дедлайн ответа: пока цепочка `PROPOSED`, на карточке пилюля «Осталось … на ответ» по `freezeDeadlineAt` (RFC3339, UTC, приходит на `PROPOSED` уже сейчас). На `FROZEN` то же поле несёт дедлайн отправки товара, поэтому таймер выводится только при `status === 'PROPOSED'` (DESIGN.md §2.7).
- Пустое состояние: «Пока нет подходящих цепочек. Попробуйте изменить запрос позже».
- Также доступен общий список цепочек пользователя вне контекста конкретного запроса (`GET /chains`, `?status=CANDIDATE` / `?status=PROPOSED,FROZEN,IN_PROGRESS`) — отдельный экран не специфицирован в текущем MVP, зарезервирован под будущий UI «Мои сделки».

**Экран цепочки — товар** (`/chains/:chainId`, макет 4.7)

- Заголовок: название получаемого товара, кнопка «Назад» (на список вариантов запроса).
- Крупное фото получаемого товара, его название, «N участников в цепочке» (`length`), `score` как индикатор вероятности (или пилюля «Цепочка собрана» при `PROPOSED` и дальше). Пока цепочка `CANDIDATE`, получаемое звено — пул кандидатов: если кандидат не один, заголовок показывает «Получаете: N вариантов».
- «Описание» получаемого товара (из `participants[].offeredItemDescription`, см. §4.4).
- На `PROPOSED` между шапкой и «Описанием» — таймер дедлайна ответа «Осталось … на ответ» по `freezeDeadlineAt` этой же цепочки (DESIGN.md §2.7); на `FROZEN`/`IN_PROGRESS` и на `CANDIDATE` его нет.
- Кнопка «Посмотреть всю цепочку» → экран схемы участников (`/chains/:chainId/participants`, макет 4.8).
- Бейдж «N/M согласий» у собранной цепочки: `N` — число участников с голосом `approved` в `participants[].vote`, `M = length` (SOFT-LOCK §7).
- Ниже — действие второго раунда (SOFT-LOCK §7): на `PROPOSED`, пока я не подтвердил, — `primary` «Требуются действия» (модалка §4.6); на `PROPOSED` после моего `approved` — статусная строка «Вы подтвердили · ждём остальных»; на `FROZEN` — плашка «Товар жёстко заблокирован…» и `primary` «Требуется действие» (→ `/chains/:chainId/deal`, §4.7); на `IN_PROGRESS` — плашка и зелёная кнопка «Перейти к сделке»; на `COMPLETED` — та же кнопка без плашки.
- Действия отклика на этом экране не дублируются — они на карточке списка (§2.6) и на схеме участников.

**Экран схемы участников** (`/chains/:chainId/participants`, макет 4.8)

- Полная карточка цепочки (`GET /chains/{chainId}`): строки по звеньям кольца (`participants`, сгруппированные по `position`). Участники анонимны — вместо имён животные-псевдонимы по позиции (§2.9).
- **`CANDIDATE`**: на каждом звене — пул кандидатов своего кластера; кандидаты не получаемого звена сворачиваются в счётчик «N вариантов», а на получаемом звене каждый кандидат откликается отдельно. Пользователь откликается на конкретную заявку (`PUT /chains/{chainId}/votes` с `{requestId, targetRequestId}`), отзыв — `DELETE` тем же телом через Modal-подтверждение. Когда кольцо откликов замыкается, цепочку переводит в `PROPOSED` сам бэкенд — клиент читает `chainStatus` из ответа и перезагружает данные.
- На `PROPOSED` и дальше над списком — пилюля «Цепочка собрана» и бейдж «N/M согласий»; в шапке каждой строки-звена — пилюля голоса второго раунда участника (SOFT-LOCK §8): «Согласился» / «Думает» / «Ожидает ответа» / «Отказался» / «Место освободилось» (вакансия после отказа). Решение участника позиции `p` лежит в `vote` участника позиции `(p + 1) % length` — голос привязан к цели голосования, а не к голосующему (§4.6), сдвиг делает фронт. Внизу — действие второго раунда: на `PROPOSED`, пока я не подтвердил, — «Требуются действия» (модалка §4.6), после моего `approved` — «Вы подтвердили · ждём остальных»; на `FROZEN`/`IN_PROGRESS` — зелёная кнопка «Перейти к сделке» (→ `/chains/:chainId/deal`, §4.7); на `COMPLETED` — та же кнопка без плашки; отклики/отзывы на кандидатах при этом не показываются.
- Ошибки `403`/`409`/`422` — тост с объяснением и повторная загрузка карточки/списка.
- Удаление/отмена выбора цепочки (`select`) отсутствует — вместо него направленный отклик (`vote`), см. §4.5.

### 2.7. Профиль / Настройки

**Экран** `/profile`

- Отображение аватара, имени, email.
- Переключатель темы (светлая/тёмная).
- Смена пароля (`/profile/password`): поля «Текущий пароль», «Новый пароль» (мин. 8 символов), «Повторите новый пароль»; после успеха — экран «Пароль изменён» с возвратом в профиль.
- Кнопка «Выйти» – вызывает `POST /auth/logout`, затем удаляет JWT из `localStorage` и перенаправляет на `/login`.

### 2.8. Общие элементы интерфейса

- **Нижняя навигация** (мобильная): «Товары», «Запросы», «Профиль».
- **Боковое меню** (десктоп): аналогичные пункты + логотип.
- **Переключатель темы** на пре-авторизационных экранах и на странице профиля; в хедере/боковом меню его нет.
- **Иконка уведомлений** с бейджем количества непрочитанных — в хедере/боковом меню (см. §2.9).
- **Тосты** для уведомлений (успех, ошибка).
- **Модальные окна** для подтверждения опасных действий (удаление товара, отмена выбора цепочки).

### 2.9. Уведомления

**Список уведомлений** (открывается по клику на иконку из §2.8)

- Список уведомлений пользователя (`GET /notifications`), непрочитанные визуально выделены.
- Открытие/клик по уведомлению помечает его прочитанным (`POST /notifications/{notificationId}/read`).
- Кнопка «Прочитать все» (`POST /notifications/read-all`).
- Пустое состояние: «Уведомлений нет».
- Уведомления — только in-app; email/push-доставка вне рамок MVP (см. §1.3).

## 3. Архитектура приложения

### 3.1. Frontend (React + TypeScript)

- **Структура**: Feature-Sliced Design (FSD)
  - `app/` – провайдеры, роутинг, глобальные стили.
  - `pages/` – страницы (экраны).
  - `features/` – пользовательские сценарии (например, создание товара, создание запроса).
  - `entities/` – бизнес-сущности (товар, запрос, пользователь).
  - `shared/` – переиспользуемые UI-компоненты, утилиты, API-клиент.
- **Стек**:
  - React 18+
  - TypeScript
  - Ant Design (UI-kit)
  - Redux Toolkit (глобальное состояние: пользователь, тема)
  - TanStack Query (работа с API, кеширование)
  - Vite (сборка)
  - ESLint + Prettier (форматирование)
- **Управление авторизацией**: JWT хранится в `localStorage`. При каждом запросе токен добавляется в заголовок `Authorization: Bearer <token>`. При старте приложения (обновление страницы) текущий пользователь восстанавливается запросом `GET /auth/me`, если токен есть в `localStorage`.

### 3.2. Backend (Golang)

- **Язык**: Go (Golang)
- **База данных**: PostgreSQL.
- **API**: RESTful с JSON-ответами.
- **Маршруты** (см. раздел 4).
- **Аутентификация**: JWT-токены, время жизни токена — 24 часа.
- **Защита**: все эндпоинты, кроме регистрации и входа, требуют валидный JWT.
- **Стенд для локальной разработки**: `make up` поднимает БД, MinIO, TEI и Go-бэкенд; фронт работает с ним через Vite-proxy (`vite.config.ts`, пустой `VITE_API_BASE_URL` → relative `/api/v1` на `:8080`) — бэкенду не нужен CORS. Отдельного мок-сервера нет.

### 3.3. DevOps

- **Контейнеризация**: Docker Compose, поднимающий:
  - Frontend (сборка через Vite, статика или dev-сервер)
  - Backend (Go-сервер)
  - База данных (PostgreSQL)
- **Переменные окружения**: порты, секреты (JWT-ключ, строки подключения).

### 3.4. Принципы разработки

_Частично основано на инженерных принципах Avito Playbook ([development-principles.md](https://github.com/avito-tech/playbook/blob/master/development-principles.md))._

- Бизнес-логика реализуется в коде бэкенда, не на стороне БД: без хранимых процедур и триггеров с бизнес-правилами. В PostgreSQL — данные и ограничения целостности (constraints, foreign keys).
- У каждой сущности — один источник правды в БД. Клиент не хранит собственных копий серверных данных, которые могут разойтись с сервером; кеш TanStack Query — временный и инвалидируется после мутаций.
- Миграции обратно совместимы: во время раскатки старая и новая версия бэкенда должны одинаково работать с текущей схемой БД (сначала совместимая миграция, потом код, который на неё опирается).
- Изменение считается готовым, когда оно покрыто тестом или проверено вручную по сценарию из `PROJECT.md`; непротестированное изменение не мёржится.
- Неиспользуемый код, эндпоинты и поля моделей удаляются сразу, а не остаются «на будущее».

## 4. API (эндпоинты)

Согласованный контракт с бэкендом (источник: `API-frontend.md`, актуализировано 2026-08-06). Черновой REST-контракт — детали (справочник категорий, точные enum'ы, разбивка ответов) уточняются по ходу интеграции. Все эндпоинты возвращают JSON. Все эндпоинты, кроме `/auth/register`, `/auth/login` и восстановления пароля (§4.1), требуют авторизации (`Authorization: Bearer <token>`). Frontend не считает граф, score, кластеры или дедлайны сам — получает готовое состояние от backend.

### 4.1. Аутентификация и пользователи

| Метод | Эндпоинт                       | Описание                                                                | Тело запроса                                                                             | Ответ (успех)                                  |
| ----- | ------------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------- |
| POST  | `/api/v1/auth/register`        | Регистрация и создание сессии (не защищён)                              | `{"fullName":"string","email":"string","password":"string"}`                             | `{"token":"jwt","user":{...}}`                 |
| POST  | `/api/v1/auth/login`           | Вход (не защищён)                                                       | `{"email":"string","password":"string"}`                                                 | `{"token":"jwt","user":{...}}`                 |
| POST  | `/api/v1/auth/logout`          | Завершить текущую сессию                                                | –                                                                                        | `{"message":"logged_out"}`                     |
| GET   | `/api/v1/auth/me`              | Текущий пользователь (используется для восстановления сессии, см. §3.1) | –                                                                                        | `{"id":"uuid","fullName":"...","email":"..."}` |
| POST  | `/api/v1/auth/change-password` | Смена пароля авторизованного пользователя                               | `{"currentPassword":"string","newPassword":"string","newPasswordConfirmation":"string"}` | `{"message":"password_changed"}`               |

Конкретные коды/сообщения ошибок входа и смены пароля определяются бэкендом; frontend ориентируется на общий формат ошибок (§4.10) — как минимум `401` для неверных данных входа, `400`/`422` для ошибки смены пароля.

**Восстановление пароля** — код из 6 цифр на email, три шага (запрос кода → проверка кода → установка пароля). Все три эндпоинта не защищены:

| Метод | Эндпоинт                                            | Описание                                 | Тело запроса                                             | Ответ (успех)                    |
| ----- | --------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------- | -------------------------------- |
| POST  | `/api/v1/account/password-recovery/send-code/`      | Отправить код восстановления на email    | `{"email":"string"}`                                     | `{"message":"code_sent"}`        |
| POST  | `/api/v1/account/password-recovery/verify-code/`    | Проверить код перед вводом нового пароля | `{"email":"string","code":"string"}`                     | `{"message":"code_valid"}`       |
| POST  | `/api/v1/account/password-recovery/reset-password/` | Установить новый пароль по коду          | `{"email":"string","code":"string","password":"string"}` | `{"message":"password_changed"}` |

Код живёт 10 минут и гасится после успешного сброса. Ошибки: `404` — email не зарегистрирован, `400` — неверный или истёкший код либо пароль короче 8 символов. Экранам этого флоу соответствует `DESIGN.md` §4.1 (`/forgot-password`, `RecoveryFlow.tsx`).

Черновик `API-frontend.md` описывает восстановление иначе — `/auth/forgot-password` + `/auth/reset-password` с одноразовым токеном из письма, без шага проверки кода и с полем `newPasswordConfirmation`. Согласовано, что бэкенд приводит ручки к варианту выше (код + отдельная проверка), а фронтенд и мок остаются как есть.

Восстановление пароля требует работающего SMTP: бэкенд шлёт код письмом и не возвращает его в
ответе. Для локальной разработки без почтового сервера в `docker-compose.yml` добавляется
`maildev` (веб-морда на `:1080`) — отдельная задача, цепочки она не затрагивает.

Сессия — JWT в заголовке `Authorization: Bearer <token>`. Выход теперь выполняется и на бэкенде (`POST /auth/logout`), и на клиенте (токен удаляется из `localStorage`).

### 4.2. Товары (`items`)

Эндпоинт переименован с `/products` на `/items`; модель товара — категория, фото (отдельная ручка загрузки) и статус. `id` товара — число (`int64`). Статус товара: `ACTIVE` / `UNAVAILABLE` / `ARCHIVED`. Поля `color`/`material`/`attributes` из ранних версий контракта убраны — колонок в БД нет (SCRUM-50 §6.1).

| Метод  | Эндпоинт                       | Описание                  | Тело запроса                                 | Ответ (успех)                                        |
| ------ | ------------------------------ | ------------------------- | -------------------------------------------- | ---------------------------------------------------- |
| GET    | `/api/v1/items`                | Мои товары (без архивных) | –                                            | `{"items":[{...}],"page":1,"pageSize":20,"total":N}` |
| POST   | `/api/v1/items`                | Создать товар (JSON)      | см. ниже                                     | `{"id":1, ...}` (201)                                |
| GET    | `/api/v1/items/{itemId}`       | Получить товар            | –                                            | `{"id":1, ...}`                                      |
| PATCH  | `/api/v1/items/{itemId}`       | Изменить товар (JSON)     | см. ниже                                     | `{"id":1, ...}`                                      |
| DELETE | `/api/v1/items/{itemId}`       | Архивировать товар        | –                                            | `204 No Content`                                     |
| POST   | `/api/v1/items/{itemId}/image` | Загрузить/заменить фото   | multipart: `image` (jpeg/png/webp, до 5 МиБ) | `{"id":1, "imageUrl": "...", ...}`                   |

`GET /items` принимает необязательные query-параметры: `page`, `pageSize`. Фильтра по статусу на
бэкенде нет — список приходит вместе с архивными (личный список владельца), поэтому фронт отсекает
`ARCHIVED` на клиенте.

Тело создания/изменения (JSON):

```json
{
  "title": "PlayStation 5",
  "description": "Консоль в хорошем состоянии, полный комплект",
  "category": "Электроника"
}
```

- `category` — строка (≤100 символов). Бэкенд принимает и пустую (заявки с такими товарами образуют собственный пул кандидатов), но форма требует выбрать значение. Отдельного справочника (`GET /categories`) у бэкенда нет; допустимые значения фронт держит константой `@shared/config/categories`.
- Фото не входит в JSON: загружается отдельным `POST /items/{itemId}/image`. Создание товара без фото допустимо сервером, но форма требует фото и грузит его вторым шагом сразу после создания.
- `imageUrl` — публичный URL фото в MinIO (`null`, пока фото нет).
- `embedding` frontend не передаёт — backend создаёт его сам.
- Валидация — `422`, конфликт hard-резервации — `409`.

### 4.3. Заявки на обмен

Ресурс переименован в `/exchange-offers` (миграция `000005` переименовала таблицу); внутреннее имя сущности на фронте остаётся `ExchangeRequest` (SCRUM-50 §6.2). `id` заявки — число (`int64`). Оптимистичная блокировка: каждая заявка имеет `version` (растёт при каждом изменении); `PUT` и `DELETE` обязаны передавать актуальную версию, иначе `409`.

| Метод  | Эндпоинт                                 | Описание                                                                   | Тело запроса                                                  | Ответ (успех)    |
| ------ | ---------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------- | ---------------- |
| GET    | `/api/v1/exchange-offers`                | Мои заявки (без `REMOVED`)                                                 | –                                                             | `[{...}]`        |
| POST   | `/api/v1/exchange-offers`                | Создать заявку и синхронно запустить matching                              | см. ниже                                                      | `{...}` (201)    |
| GET    | `/api/v1/exchange-offers/{id}`           | Детали заявки                                                              | –                                                             | `{...}`          |
| PUT    | `/api/v1/exchange-offers/{id}`           | Изменить заявку (полное тело, только живая заявка: `ACTIVE`/`IN_PROPOSAL`) | `{offeredItemId, wantedDescription, wantedCategory, version}` | `{...}`          |
| DELETE | `/api/v1/exchange-offers/{id}?version=N` | Деактивировать заявку (мягкое удаление → `REMOVED`; `N > 0` обязателен)    | –                                                             | `204 No Content` |

Тело создания:

```json
{
  "offeredItemId": 12,
  "wantedDescription": "Ищу ноутбук для программирования, желательно 16 ГБ RAM",
  "wantedCategory": "Электроника"
}
```

- `wantedDescription` — обязательное свободное описание желаемого.
- `wantedCategory` — строка (≤100 символов); значения из того же справочника, что и категория товара (§2.3). Бэкенд её не требует, форма — требует. В подборе не участвует: эмбеддинг желаемого строится только по `wantedDescription`.

Ответ на создание и изменение — сам объект заявки:

```json
{
  "id": 7,
  "offeredItemId": 12,
  "wantedDescription": "Ищу ноутбук...",
  "wantedCategory": "Электроника",
  "status": "ACTIVE",
  "version": 1,
  "createdAt": "2026-08-08T09:00:00Z",
  "updatedAt": "2026-08-08T09:00:00Z"
}
```

- `GET /exchange-offers` дополнительно вкладывает в каждый элемент `offeredItemTitle` — название отдаваемого товара. В детали (`GET /exchange-offers/{id}`) и в ответах создания/изменения снимка нет: фронт берёт название и фото товара из кеша `items` по `offeredItemId` — и на экране «Варианты обмена», и в карточке списка запросов.
- Прежней обёртки `{request, matching}` на реальном бэкенде нет; матчинг — заглушка, поэтому `createdCandidateChains` всегда `0` и заявка остаётся в `ACTIVE` (SCRUM-50 §5).

Статус заявки: `ACTIVE` (в поиске) → `IN_PROPOSAL` (цепочки найдены/предложены) → `LOCKED` (сделка согласована, заявка защищена от редактирования) → `DONE` / `IN_PROGRESS` / `REMOVED` (терминальные). Заявки со статусом `REMOVED` отфильтровываются сервером из списка и детали — в UI статуса «Отменён» нет. Отметка цепочки (`POST /chains/{chainId}/select`) заявку не блокирует — она обратима и не эксклюзивна.

### 4.5. Отклики на `CANDIDATE`

Отклик — направленный: пользователь отвечает на конкретную заявку следующего звена. Отдельного
действия «отказаться» нет: отсутствие отклика и есть отсутствие участия.

| Метод  | Эндпоинт                                                           | Описание                                   | Тело запроса                              | Ответ (успех) |
| ------ | ------------------------------------------------------------------ | ------------------------------------------ | ----------------------------------------- | ------------- |
| PUT    | `/api/v1/chains/{chainId}/votes`                                   | Откликнуться на кандидата следующего звена | `{"requestId":101,"targetRequestId":202}` | см. ниже      |
| DELETE | `/api/v1/chains/{chainId}/votes?requestId=101&targetRequestId=202` | Отозвать отклик (пока цепочка `CANDIDATE`) | –                                         | `204`         |

`PUT` идемпотентен: повторный отклик не ошибка, ответ такой же. Когда кольцо pending-откликов
замыкается, цепочку переводит в `PROPOSED` сам бэкенд — клиент обязан прочитать `chainStatus` из
ответа и перезагрузить данные, иначе экран покажет устаревшие действия и словит `409`.

```json
{
  "chainId": 42,
  "requestId": 101,
  "targetRequestId": 202,
  "vote": "pending",
  "votedAt": "2026-08-08T12:00:00Z",
  "chainStatus": "PROPOSED"
}
```

Коды ошибок `votes`: `404` цепочка не найдена · `403` заявка не твоя · `409` цепочка уже не
`CANDIDATE` · `422` невалидная цель/тело. `DELETE` снимает только pending-отклик кандидатной
цепочки; повторный `DELETE` успешен (идемпотентен).

### 4.6. Подтверждение мягкой блокировки (второй раунд)

Когда кольцо направленных откликов замыкается, цепочка переходит `CANDIDATE → PROPOSED` — каждый
участник обязан повторно подтвердить участие. Когда подтвердили все, бэкенд сам переводит цепочку
`PROPOSED → FROZEN`: заявки уходят в `LOCKED`, товары — в `UNAVAILABLE`, конкурирующие цепочки
вычёркивают этих участников. Повторный `confirm` у уже замороженной цепочки идемпотентен — успех.

| Метод | Эндпоинт                           | Описание             | Тело запроса | Ответ (успех) |
| ----- | ---------------------------------- | -------------------- | ------------ | ------------- |
| POST  | `/api/v1/chains/{chainId}/confirm` | Подтвердить участие  | –            | см. ниже      |
| POST  | `/api/v1/chains/{chainId}/think`   | Отложить решение     | –            | см. ниже      |
| POST  | `/api/v1/chains/{chainId}/decline` | Отказаться от сделки | –            | см. ниже      |

```json
{ "chainId": 42, "status": "FROZEN" }
```

`status` — `PROPOSED` (подтвердили ещё не все) или `FROZEN` (все подтвердили — цепочка
заморожена). Коды ошибок: `404` цепочка не найдена · `403` не участник · `409` цепочка
не `PROPOSED` или заявка уже в двух замороженных цепочках.

Ответ `think`:

```json
{ "chainId": 42, "vote": "thinking" }
```

«Я подумаю» — серверное состояние, а не клиентское: `POST /think` пишет голос `thinking`
(четвёртое значение `VoteValue` наравне с `pending`/`approved`/`rejected`), переживает перезагрузку
страницы и читается на всех трёх экранах. Требует `PROPOSED`; коды ошибок — как у `confirm`
(SOFT-LOCK §3.2).

Ответ `decline`:

```json
{ "chainId": 42, "status": "CANDIDATE", "replacementAvailable": false }
```

Отказ не всегда ломает цепочку — исход выбирает бэкенд (SOFT-LOCK §3.2): `BROKEN` (в цепочке уже
была незакрытая вакансия — заявки возвращаются в `ACTIVE`, цепочка удаляется), `PROPOSED` +
`replacementAvailable: true` (все остальные подтвердили, замена есть — цепочка живёт с вакансией,
подобрать замену может только предыдущий по кольцу участник) или `CANDIDATE` (откат: заявки в
`ACTIVE`, голоса второго раунда в `pending`). Голос отказавшегося удаляется, поэтому состояние
«я отказался, а цепочка ещё `PROPOSED`» ему недоступно. Коды ошибок — как у `confirm`.

**Голоса второго раунда** (`213336c`): `GET /chains` и `GET /chains/{id}` отдают `vote` **всех**
участников в `participants[].vote`. Голос привязан к **цели** голосования, а не к голосующему:
строка `votes` — ребро «я → тот, у кого получаю», раскладывается по участнику с
`requestId == target_request_id`. Поэтому решение участника позиции `p` лежит в `vote` участника
позиции `(p + 1) % length` — сдвиг делает фронт (SOFT-LOCK §3.3). Свои поля `myVote`/`confirmVote`
**не заводятся**. На `PROPOSED`/`FROZEN` в `participants[]` ровно один участник на позицию;
пустой `vote` у участника позиции `p` — вакансия на позиции `(p − 1 + length) % length` (голос
отказавшегося удалён). Счётчик согласий «N/M» — число участников с `vote === 'approved'`.
На кандидатной цепочке `vote` остаётся откликом первого раунда (всегда `pending`).

> Не реализовано на бэкенде (ожидает контракт, SOFT-LOCK §3.1): счётчик согласий `approvedVotes`
> в ответе `exchange-options` (на 4.6 `PROPOSED` фронт считает его из `participants[].vote` детали
> `GET /chains/{id}`). `freezeDeadlineAt` в `exchange-options` тоже не приходит — 4.6 берёт дедлайн
> из той же детали; на `PROPOSED` бэкенд отдаёт его в `GET /chains` и `GET /chains/{id}` уже сейчас,
> а просроченную цепочку снимает с блокировки лениво (клиент видит `410` только на мутациях).

### 4.7. Отправка и получение товаров (исполнение сделки)

После заморозки (`FROZEN`) цепочка исполняется: участники отправляют товары, получатели их
забирают. Физического ПВЗ в MVP нет — в проде подтверждение отправки/получения даёт интеграция с
Авито, в интерфейсе это кнопки-заглушки «Я отправил товар» и «Я забрал товар», которые дёргают те
же ручки (DEAL-PLAN §4.5).

| Метод | Эндпоинт                              | Авторизация | Описание                     | Тело запроса                  |
| ----- | ------------------------------------- | ----------- | ---------------------------- | ----------------------------- |
| POST  | `/api/v1/integrations/avito/handoffs` | нет         | Подтвердить отправку товара  | `{"chainId":1,"requestId":2}` |
| POST  | `/api/v1/chains/{chainId}/receipt`    | Bearer      | Подтвердить получение товара | `{"requestId":2}`             |

Ответ обеих:

```json
{ "chainId": 1, "requestId": 2, "status": "IN_PROGRESS" }
```

`status` — новый статус цепочки. Семантика `requestId` различается:

- `handoffs` — `requestId` **своей** заявки (`chain.currentRequestId`): «я отдал свой товар». Заявка
  `LOCKED → IN_PROGRESS`, цепочка `FROZEN → IN_PROGRESS`.
- `receipt` — `requestId` заявки **звена-источника**, то есть участника на
  `receivesFromPosition` (`receivesItem(chain)[0].requestId`): «я забрал товар, который отправлял он».
  Заявка источника `IN_PROGRESS → DONE`. Когда все заявки цепочки `DONE`, цепочка `COMPLETED`.
- Получение возможно только после отправки: если заявка источника ещё `LOCKED`, ответ
  `409 «передача товара ещё не подтверждена»`.

Статус заявки участника (`requestStatus` в `chainParticipantResponse` запроса `GET /chains/{id}`) —
единственный источник состояния экрана сделки (DEAL-PLAN §5.1): `LOCKED` — товар не отправлен,
`IN_PROGRESS` — отправлен («в ПВЗ»), `DONE` — получатель подтвердил получение.

Коды ошибок: `403` «только получатель товара может подтвердить его получение» · `404` цепочка не
найдена · `409` «цепочка не готова к передаче товаров» / «передача товара ещё не подтверждена» ·
`422` «заявка не является закреплённым товаром этой цепочки».

### 4.8. Замена участника

| Метод | Эндпоинт                                                             | Описание                       | Тело запроса | Ответ (успех)            |
| ----- | -------------------------------------------------------------------- | ------------------------------ | ------------ | ------------------------ |
| GET   | `/api/v1/chains/{chainId}/replacement-candidates`                    | Получить допустимые замены     | –            | `[{...}]`                |
| POST  | `/api/v1/chains/{chainId}/replacement-candidates/{requestId}/select` | Выбрать и пригласить замену    | –            | `{"message":"invited"}`  |
| POST  | `/api/v1/chains/{chainId}/replacement-invitation/accept`             | Кандидат принимает приглашение | –            | `{"message":"accepted"}` |
| POST  | `/api/v1/chains/{chainId}/replacement-invitation/decline`            | Кандидат отказывается          | –            | `{"message":"declined"}` |

В список replacement candidates попадают уже отфильтрованные backend'ом заявки: участники псевдокластера, совместимые с предыдущим и следующим звеном цепи, активные и без резервирования.

### 4.9. Уведомления

| Метод | Эндпоинт                                      | Описание             | Тело запроса | Ответ (успех)                                    |
| ----- | --------------------------------------------- | -------------------- | ------------ | ------------------------------------------------ |
| GET   | `/api/v1/notifications`                       | Мои уведомления      | –            | `[{"id":"uuid","text":"...","read":false, ...}]` |
| POST  | `/api/v1/notifications/{notificationId}/read` | Пометить прочитанным | –            | `{"message":"read"}`                             |
| POST  | `/api/v1/notifications/read-all`              | Прочитать все        | –            | `{"message":"read_all"}`                         |

### 4.10. Общие ошибки

| Код | Когда показывать                                         |
| --- | -------------------------------------------------------- |
| 401 | Сессия истекла — отправить на `/login`                   |
| 403 | Пользователь не участник цепочки / не владелец ресурса   |
| 404 | Ресурс отсутствует или недоступен                        |
| 409 | Конфликт: товар уже в резерве, цепочка успела измениться |
| 410 | Deadline истёк, цепочка откатилась                       |
| 422 | Ошибка валидации полей                                   |

Для `409` и `410` frontend лучше показывает сообщение и повторно загружает карточку цепочки.

## 7. Требования к бэкенду

### 7.1. База данных

- PostgreSQL: структурированная схема, транзакции, целостность данных на уровне БД.
- Схема: пользователи, товары (items), запросы, цепочки, уведомления (см. модели ниже).
- Миграции – с использованием `golang-migrate`.

### 7.2. Модели данных (сущности)

- **User**: id, full_name, email, password_hash, created_at.
- **Item** (ранее Product, эндпоинт `/items`): id (int64), user_id, title, description, category (текст), image_url, embedding (вычисляется бэкендом), status (ACTIVE, UNAVAILABLE, ARCHIVED), created_at, updated_at.
- **ExchangeRequest** (ресурс `/exchange-offers`): id (int64), user_id, offered_item_id, wanted_description, wanted_category (текст), status (ACTIVE, IN_PROPOSAL, LOCKED, DONE, IN_PROGRESS, REMOVED), version (оптимистичная блокировка), created_at, updated_at.
- **Chain**: id, status (CANDIDATE, PROPOSED, FROZEN, IN_PROGRESS, COMPLETED, ...), score (0–1), freeze_deadline_at, participants (JSON: position, request_id, offered_item, receives_from_position, request_status, vote), created_at. Кандидатные цепочки генерируются matching-алгоритмом синхронно при создании заявки (§4.3); дальнейшие переходы статуса — по действиям участников: отклики (§4.5), повторное подтверждение (§4.6), отправка/получение товаров (§4.7), замена участника (§4.8).
- **Notification**: id, user_id, text, read (bool), created_at.

### 7.3. Обработка ошибок

- Единый формат ошибок: `{"error": "message", "code": 400}`.
- Структурированное логирование ошибок на уровне приложения.

### 7.4. Деплой

- Dockerfile для бэкенда (многоступенчатая сборка).
- Docker Compose для подъёма всех сервисов (фронт, бэк, БД).
