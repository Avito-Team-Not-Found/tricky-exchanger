# Техническое задание (ТЗ) на разработку MVP сервиса многостороннего бартера

---

## 1. Введение

### 1.1. Цель проекта

Создать MVP веб‑приложения для многостороннего обмена (бартера) вещами. Пользователь может добавить свои товары, создать запрос на обмен, увидеть возможные цепочки обмена и выбрать подходящую. Сервис делает схему обмена прозрачной, поддерживает доверие участников и позволяет управлять процессом.

### 1.2. Бизнес-задача

- Помочь пользователю обменять ненужную вещь на желаемую.
- Объединять пользователей в цепочки, где каждый отдаёт одну вещь и получает другую.
- Обеспечить понятный и безопасный сценарий обмена.

### 1.3. Ограничения MVP

- Согласование цепочек между участниками (подтверждение, статусы участия) в продукте отсутствует. Выбор цепочки — это индикация предпочтения пользователя: не блокирует другие цепочки и не резервирует товары. Пользователь может быть выбран одновременно в нескольких цепочках.
- Вне рамок MVP: чат между участниками, история обменов, рейтинги и отзывы, email/push-уведомления.

## 2. Функциональные требования (экраны и сценарии)

### 2.1. Авторизация

**Экран входа** (`/login`)

- Поля: Email, Пароль.
- Кнопка «Войти».
- Ссылка «Зарегистрироваться» → переход на экран регистрации.
- При успешном входе – редирект на главный экран (список товаров).

**Экран регистрации** (`/register`)

- Поля: Имя, Email, Пароль (минимум 8 символов), Подтверждение пароля.
- Кнопка «Зарегистрироваться».
- Ссылка «Уже есть аккаунт? Войти» → переход на экран входа.
- После регистрации – автоматический вход и редирект на главный.

**Защита маршрутов**: все страницы, кроме `/login` и `/register`, доступны только авторизованным пользователям. Неавторизованный пользователь перенаправляется на `/login`.

### 2.2. Главный экран – список товаров пользователя

**Экран** `/products`

- Отображает все товары текущего пользователя.
- Каждая карточка товара содержит: фото (превью), название, статус (`активен`, `забронирован`, `обменян`).
- Иконки редактирования и удаления (доступны по наведению / долгому нажатию).
- Кнопка «+» (добавить товар) в хедере или плавающая кнопка.
- Пустое состояние: «У вас пока нет товаров. Нажмите «+», чтобы добавить».

### 2.3. Создание / редактирование товара

**Экран создания** (`/products/new`) и **редактирования** (`/products/:id/edit`)

- Заголовок: «Новый товар» или «Редактирование товара».
- Кнопка «Назад» → возврат на список товаров.
- Поля:
  - Фото (можно несколько, минимум одно) – загрузчик с превью.
  - Название (обязательное, до 100 символов).
  - Описание (обязательное, до 500 символов).
  - Состояние (выпадающий список): `Новый`, `Как новый`, `Б/у`, `Требует ремонта`.
- Кнопка «Сохранить» – активна только при заполнении всех обязательных полей.
- После сохранения – тост об успехе и редирект на `/products`.

### 2.4. Создание запроса на обмен

**Экран создания запроса** (`/exchange-requests/new`)

- Заголовок: «Новый запрос», кнопка «Назад».
- Блок «Что вы отдаёте?»:
  - Если у пользователя есть товары – отображается список его товаров с возможностью выбора (радио-кнопка или карточки с выбором).
  - Если товаров нет – показывается кнопка «Создать новый товар», которая открывает экран создания товара (после сохранения автоматически возвращает в форму запроса с выбором созданного товара).
- Блок «Что вы хотите получить?»:
  - Поле «Название желаемого товара» (обязательное).
  - Поле «Описание желаемого» (необязательное).
  - Поле «Состояние» (выпадающий список, аналогично товару).
- Кнопка «Создать запрос» – активна при выборе отдаваемого товара и заполнении названия желаемого.
- После создания – тост об успехе, редирект на экран «Мои запросы».

### 2.5. Мои запросы

**Экран** `/exchange-requests`

- Заголовок: «Мои запросы», кнопка «+» для создания нового.
- Список запросов в виде карточек:
  - Отдаваемый товар (фото, название) → желаемый товар (название).
  - Статус (тег): `Активен`, `В процессе`, `Завершён`, `Отменён`.
  - Кнопка/ссылка «Подробнее» → переход на экран конкретного запроса.
- Пустое состояние: «У вас нет запросов. Создайте новый».

### 2.6. Просмотр запроса и список цепочек

**Экран** `/exchange-requests/:requestId`

- Заголовок: «Варианты обмена», кнопка «Назад».
- Компактный блок с информацией о запросе: «Вы отдаёте [товар] → хотите получить [желаемый]».
- Список доступных цепочек (моковые данные), отсортированных по убыванию вероятности успеха.
- **Карточка цепочки** содержит:
  - Визуализацию цепочки (аватары участников, стрелки, миниатюры товаров).
  - Длину (например, «3 участника»).
  - Вероятность успеха (цветовой индикатор + процент).
  - Статус участия пользователя: «Вы не выбрали» (кнопка «Выбрать эту цепочку») или «Выбрана» (кнопка «Отменить выбор»). Выбор не влияет на другие цепочки и не блокирует их.
- Пустое состояние: «Пока нет подходящих цепочек. Попробуйте изменить запрос позже».

### 2.7. Профиль / Настройки

**Экран** `/profile`

- Отображение аватара, имени, email.
- Переключатель темы (светлая/тёмная).
- Кнопка «Выйти» – выполняет выход (удаляет JWT) и перенаправляет на `/login`.

### 2.8. Общие элементы интерфейса

- **Нижняя навигация** (мобильная): «Товары», «Запросы», «Профиль».
- **Боковое меню** (десктоп): аналогичные пункты + логотип.
- **Переключатель темы** присутствует в хедере и на странице профиля.
- **Тосты** для уведомлений (успех, ошибка).
- **Модальные окна** для подтверждения опасных действий (удаление товара, отмена выбора цепочки).

## 3. Архитектура приложения

### 3.1. Frontend (React + TypeScript)

- **Структура**: Feature-Sliced Design (FSD)
  - `app/` – провайдеры, роутинг, глобальные стили.
  - `pages/` – страницы (экраны).
  - `features/` – пользовательские сценарии (например, создание товара, создание запроса).
  - `entities/` – бизнес-сущности (товар, запрос, пользователь).
  - `shared/` – переиспользуемые UI-компоненты, утилиты, API-клиент.
- **Стек**:
  - React 18+
  - TypeScript
  - Ant Design (UI-kit)
  - Redux Toolkit (глобальное состояние: пользователь, тема)
  - TanStack Query (работа с API, кеширование)
  - Vite (сборка)
  - ESLint + Prettier (форматирование)
- **Управление авторизацией**: JWT хранится в `localStorage`. При каждом запросе токен добавляется в заголовок `Authorization: Bearer <token>`.

### 3.2. Backend (Golang)

- **Язык**: Go (Golang)
- **База данных**: PostgreSQL.
- **API**: RESTful с JSON-ответами.
- **Маршруты** (см. раздел 4).
- **Аутентификация**: JWT-токены, время жизни токена — 24 часа.
- **Защита**: все эндпоинты, кроме регистрации и входа, требуют валидный JWT.
- **Мокирование на этапе фронтенд-разработки**: до готовности бэкенда фронтенд работает с мок-сервером (`json-server` на фикстурах, повторяющих контракты раздела 4). Мок-сервер живёт в `frontend/mock/` (`server.js` + фикстуры `db.json`, `passwords.json`), запускается через `npm run mock` и слушает `http://localhost:4000` (`VITE_API_BASE_URL` в `.env.development`). После интеграции с реальным API мок-сервер не используется.

### 3.3. DevOps

- **Контейнеризация**: Docker Compose, поднимающий:
  - Frontend (сборка через Vite, статика или dev-сервер)
  - Backend (Go-сервер)
  - База данных (PostgreSQL)
- **Переменные окружения**: порты, секреты (JWT-ключ, строки подключения).

### 3.4. Принципы разработки

_Частично основано на инженерных принципах Avito Playbook ([development-principles.md](https://github.com/avito-tech/playbook/blob/master/development-principles.md))._

- Бизнес-логика реализуется в коде бэкенда, не на стороне БД: без хранимых процедур и триггеров с бизнес-правилами. В PostgreSQL — данные и ограничения целостности (constraints, foreign keys).
- У каждой сущности — один источник правды в БД. Клиент не хранит собственных копий серверных данных, которые могут разойтись с сервером; кеш TanStack Query — временный и инвалидируется после мутаций.
- Миграции обратно совместимы: во время раскатки старая и новая версия бэкенда должны одинаково работать с текущей схемой БД (сначала совместимая миграция, потом код, который на неё опирается).
- Изменение считается готовым, когда оно покрыто тестом или проверено вручную по сценарию из `PROJECT.md`; непротестированное изменение не мёржится.
- Неиспользуемый код, эндпоинты и поля моделей удаляются сразу, а не остаются «на будущее».

## 4. API (эндпоинты)

Все эндпоинты возвращают JSON. Для незащищённых эндпоинтов указано особо.

### 4.1. Авторизация и пользователи

| Метод | Эндпоинт                        | Описание                      | Тело запроса                                             | Ответ (успех)                              |
| ----- | ------------------------------- | ----------------------------- | -------------------------------------------------------- | ------------------------------------------ |
| POST  | `/api/v1/account/registration/` | Регистрация (не защищён)      | `{"email":"string","password":"string","name":"string"}` | `{"token":"jwt","user":{...}}`             |
| POST  | `/api/v1/account/login/`        | Вход (не защищён)             | `{"email":"string","password":"string"}`                 | `{"token":"jwt","user":{...}}`             |
| GET   | `/api/v1/users/{id}`            | Получение данных пользователя | –                                                        | `{"id":"uuid","name":"...","email":"..."}` |

Сессия — только JWT, без хранения на сервере. Выход выполняется на клиенте (токен удаляется из `localStorage`), серверный эндпоинт для этого не нужен.

### 4.2. Товары

| Метод  | Эндпоинт                | Описание                             | Тело запроса                                                                            | Ответ (успех)                                                                            |
| ------ | ----------------------- | ------------------------------------ | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| GET    | `/api/v1/products`      | Список товаров текущего пользователя | –                                                                                       | `[{"id":"uuid","title":"...","description":"...","image":"url","status":"active", ...}]` |
| GET    | `/api/v1/products/{id}` | Детали товара                        | –                                                                                       | `{"id":"uuid","title":"...","description":"...","image":"url","status":"..."}`           |
| POST   | `/api/v1/products`      | Создание товара                      | `multipart/form-data` с полями `title`, `description`, `image` (файл)                   | `{"id":"uuid","title":"...","description":"...","image":"url"}`                          |
| PATCH  | `/api/v1/products/{id}` | Обновление товара (частичное)        | `{"title":"string"\|"description":"string"\|"image":"file"\|null}` (один или несколько) | `{"id":"uuid","title":"...","description":"...","image":"url"}`                          |
| DELETE | `/api/v1/products/{id}` | Удаление товара                      | –                                                                                       | `{"message":"deleted"}`                                                                  |

### 4.3. Запросы на обмен

| Метод  | Эндпоинт                                       | Описание                                 | Тело запроса                                                                   | Ответ (успех)                                                                                                                         |
| ------ | ---------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/exchange-requests/{requestId}`        | Детали запроса                           | –                                                                              | `{"id":"uuid","offeredItemId":"uuid","offeredItem":{...},"wantedDescription":"string","wantedState":"string","status":"active", ...}` |
| GET    | `/api/v1/exchange-requests`                    | Список запросов текущего пользователя    | –                                                                              | `[{"id":"uuid","offeredItem":{...},"wantedDescription":"...","status":"active"}]`                                                     |
| POST   | `/api/v1/exchange-requests`                    | Создание запроса                         | `{"offeredItemId":"uuid","wantedDescription":"string","wantedState":"string"}` | `{"id":"uuid", ...}`                                                                                                                  |
| POST   | `/api/v1/exchange-requests/{requestId}/cancel` | Отмена запроса                           | –                                                                              | `{"message":"cancelled"}`                                                                                                             |
| PATCH  | `/api/v1/exchange-requests/{requestId}`        | Обновление запроса (только если активен) | `{"wantedDescription":"string","wantedState":"string"}`                        | `{"id":"uuid", ...}`                                                                                                                  |
| DELETE | `/api/v1/exchange-requests/{requestId}`        | Удаление запроса                         | –                                                                              | `{"message":"deleted"}`                                                                                                               |

**Примечание:** все эндпоинты (кроме /account/*) требуют JWT в заголовке `Authorization: Bearer <token>`.

### 4.4. Цепочки

Цепочки генерируются бэкендом (фиктивный алгоритм подбора, без реального поиска совпадений между пользователями) один раз при первом запросе списка для данного `exchange request` и сохраняются, чтобы выбор пользователя переживал перезагрузку страницы.

| Метод | Эндпоинт                                                          | Описание                   | Тело запроса | Ответ (успех)                                                                                                                                                                                |
| ----- | ----------------------------------------------------------------- | -------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/v1/exchange-requests/{requestId}/chains`                    | Список цепочек для запроса | –            | `[{"id":"uuid","length":3,"successProbability":85,"selected":false,"participants":[{"userId":"uuid","name":"...","offers":{"id":"...","title":"..."},"wants":{"id":"...","title":"..."}}]}]` |
| POST  | `/api/v1/exchange-requests/{requestId}/chains/{chainId}/select`   | Выбрать цепочку            | –            | `{"id":"uuid","selected":true}`                                                                                                                                                              |
| POST  | `/api/v1/exchange-requests/{requestId}/chains/{chainId}/deselect` | Отменить выбор цепочки     | –            | `{"id":"uuid","selected":false}`                                                                                                                                                             |

**Формат цепочки:**

- `id` – идентификатор цепочки.
- `length` – количество участников.
- `successProbability` – число от 0 до 100.
- `selected` – выбрана ли цепочка текущим пользователем.
- `participants` – массив участников с их отдаваемыми и желаемыми товарами (для текущего пользователя поля `offers` и `wants` соответствуют его товарам).

## 5. Управление состоянием и данные

### 5.1. Redux Toolkit

- **Слайсы**:
  - `user` – данные авторизованного пользователя, токен.
  - `theme` – текущая тема (светлая/тёмная).
- Другие данные (список товаров, запросы) хранятся в кеше TanStack Query.

### 5.2. TanStack Query

- Используется для всех запросов к API.
- Автоматическое обновление после мутаций (инвалидация ключей).
- Отдельные хуки для каждого эндпоинта.

### 5.3. Защита маршрутов

- Компонент-обёртка `PrivateRoute`, проверяющий наличие токена. При отсутствии – редирект на `/login`.

## 7. Требования к бэкенду

### 7.1. База данных

- PostgreSQL: структурированная схема, транзакции, целостность данных на уровне БД.
- Схема: пользователи, товары, запросы, цепочки (см. модели ниже).
- Миграции – с использованием `golang-migrate`.

### 7.2. Модели данных (сущности)

- **User**: id, name, email, password_hash, created_at.
- **Product**: id, user_id, title, description, image_url, status (active, reserved, exchanged), created_at, updated_at.
- **ExchangeRequest**: id, user_id, offered_product_id, wanted_description, wanted_state, status (active, in_progress, completed, cancelled), created_at, updated_at.
- **Chain**: id, request_id, participants (JSON), success_probability, selected (bool, выбор текущего пользователя), created_at. Генерируется один раз на запрос (см. 4.4), дальнейший пересчёт не выполняется.

### 7.3. Обработка ошибок

- Единый формат ошибок: `{"error": "message", "code": 400}`.
- Структурированное логирование ошибок на уровне приложения.

### 7.4. Деплой

- Dockerfile для бэкенда (многоступенчатая сборка).
- Docker Compose для подъёма всех сервисов (фронт, бэк, БД).
