# Техническое задание (ТЗ) на разработку MVP сервиса многостороннего бартера

---

## 1. Введение

### 1.1. Цель проекта

Создать MVP веб‑приложения для многостороннего обмена (бартера) вещами. Пользователь может добавить свои товары, создать запрос на обмен, увидеть возможные цепочки обмена и выбрать подходящую. Сервис делает схему обмена прозрачной, поддерживает доверие участников и позволяет управлять процессом.

### 1.2. Бизнес-задача

- Помочь пользователю обменять ненужную вещь на желаемую.
- Объединять пользователей в цепочки, где каждый отдаёт одну вещь и получает другую.
- Обеспечить понятный и безопасный сценарий обмена.

### 1.3. Ограничения MVP

- Цепочка проходит согласованный жизненный цикл подтверждения между участниками (см. §4.4–4.7): кандидатная цепочка (`CANDIDATE`) → отклики участников «принять/отклонить» → после всех согласий — мягкая блокировка с подтверждением участия до дедлайна (`freeze-votes`) → `FROZEN`; при отказе или истечении дедлайна доступна замена выбывшего участника (`replacement-candidates`). Выбор пользователем цепочки (`select`) переводит её в `PROPOSED` и резервирует его участие в ней на время цикла согласования — в отличие от более ранней версии MVP, где выбор ни на что не влиял.
- Вне рамок MVP: чат между участниками, история обменов, рейтинги и отзывы, доставка уведомлений по email/push (in-app уведомления — часть контракта, см. §4.8, §2.9).

## 2. Функциональные требования (экраны и сценарии)

### 2.1. Авторизация

**Экран входа** (`/login`)

- Поля: Email, Пароль.
- Кнопка «Войти».
- При успешном входе – редирект на главный экран (список товаров).

**Экран регистрации** (`/register`)

- Поля: Имя, Email, Пароль (минимум 8 символов), Подтверждение пароля.
- Кнопка «Зарегистрироваться».
- После регистрации – автоматический вход и редирект на главный.
- Переключение между входом и регистрацией — таб-переключателем над формой.

**Защита маршрутов**: все страницы, кроме `/login` и `/register`, доступны только авторизованным пользователям. Неавторизованный пользователь перенаправляется на `/login`.

### 2.2. Главный экран – список товаров пользователя

**Экран** `/products`

- Отображает все товары текущего пользователя.
- Каждая карточка товара содержит: фото (превью), название, статус (`активен`, `забронирован`, `обменян`); категория опционально показывается бейджем (товар теперь имеет `categoryId`, `condition`, `color`, `material`, `attributes` — см. §2.3, §7.2).
- Иконки редактирования и удаления (доступны по наведению / долгому нажатию).
- Кнопка «+» (добавить товар) в хедере или плавающая кнопка.
- Пустое состояние: «У вас пока нет товаров. Нажмите «+», чтобы добавить».

### 2.3. Создание / редактирование товара

**Экран создания** (`/products/new`) и **редактирования** (`/products/:id/edit`)

- Заголовок: «Новый товар» или «Редактирование товара».
- Кнопка «Назад» → возврат на список товаров.
- Поля:
  - Фото (один загрузчик с превью и возможностью замены/удаления, обязательное) – в мобильном макете один снимок, контракт допускает несколько.
  - Название (`title`, обязательное, до 100 символов).
  - Описание (`description`, обязательное, до 500 символов).
  - Категория (`categoryId`, необязательное в текущем MVP — справочник категорий не входит в согласованный контракт §4; мок отдаёт статичный каталог `GET /api/v1/categories`, уточнить у бэкенда).
  - Состояние (`condition`, обязательное, выпадающий список): `Новый` / `Как новый` / `Б/у` / `Требует ремонта` (enum: `NEW`, `LIKE_NEW`, `USED`, `NEEDS_REPAIR`).
  - Цвет (`color`, необязательное, текст) и Материал (`material`, необязательное, может быть `null`) — корректно редактируются при изменении товара.
  - Атрибуты (`attributes`, необязательное, набор полей, зависящих от категории — например, объём накопителя и наличие коробки для электроники; в текущем UI не редактируются).
- `embedding` товара frontend не передаёт и не показывает — backend вычисляет его сам.
- Кнопка «Сохранить» – активна только при заполнении всех обязательных полей.
- После сохранения – тост об успехе и редирект на `/products`.

### 2.4. Создание запроса на обмен

**Экран создания запроса** (`/exchange-requests/new`)

- Заголовок: «Новый запрос», кнопка «Назад».
- Блок «Что вы отдаёте?»:
  - Если у пользователя есть товары – отображается список его товаров с возможностью выбора (радио-кнопка или карточки с выбором).
  - Если товаров нет – показывается кнопка «Создать новый товар», которая открывает экран создания товара (после сохранения автоматически возвращает в форму запроса с выбором созданного товара).
- Блок «Что вы хотите получить?»:
  - Поле «Что вы хотите получить» (`wantedDescription`, обязательное, свободный текст, до 500 символов — заменяет прежние отдельные поля «название» + «описание» желаемого).
  - Необязательный блок уточнения фильтра для мэтчинга (`wantedProfile`): категория (`categoryId`), допустимые состояния (`acceptableCondition`, чекбоксы аналогично состоянию товара), специфичные для категории фильтры (например, минимальный объём ОЗУ для категории «Ноутбуки»). Поле необязательное целиком — если не заполнено, matching идёт только по тексту `wantedDescription`.
- Кнопка «Создать запрос» – активна при выборе отдаваемого товара и заполнении текста желаемого; повторная отправка при активном запросе недопустима (кнопка блокируется на время сабмита).
- После создания matching запускается синхронно на бэкенде; фронт показывает результат: **«Найдено N подходящих цепочек»** (заявка переходит в `IN_PROPOSAL`) или **«Пока подходящих цепочек нет — заявка остаётся в поиске»** (`ACTIVE`).
- Если у пользователя нет товаров — вместо выбора отдаваемого товара показывается кнопка «Создать новый товар» (ведёт на `/products/new?returnTo=request`); после сохранения товара пользователь возвращается в форму запроса с выбором созданного товара.

**Экран редактирования запроса** (`/exchange-requests/:requestId/edit`)

- Те же поля, что при создании (кроме выбора отдаваемого товара — он фиксирован).
- Живая заявка (`ACTIVE`/`IN_PROPOSAL`) редактируется: PATCH пересчитывает локальное окружение и запускает matching заново.
- **`LOCKED`-заявка визуально защищена от обычного редактирования**: форма отображается в read-only, сверху баннер «Заявка заблокирована и защищена от редактирования», кнопка сохранения недоступна. `DONE`/`REMOVED` тоже не редактируются.

### 2.5. Мои запросы

**Экран** `/exchange-requests`

- Заголовок: «Мои запросы», кнопка «+» для создания нового.
- Список запросов в виде карточек:
  - Отдаваемый товар (фото, название) → желаемый товар (название).
  - Статус (тег): `Активен`, `В процессе`, `Заблокирован`, `Завершён`, `Отменён` (см. §4.3).
  - Тап по карточке → экран редактирования запроса (§2.4); у живой заявки есть действие «Удалить» (soft-delete → `REMOVED`).
- Пустое состояние: «У вас нет запросов. Создайте новый».

### 2.6. Просмотр запроса, список цепочек и их согласование

**Экран** `/exchange-requests/:requestId`

- Заголовок: «Варианты обмена», кнопка «Назад».
- Компактный блок с информацией о запросе: «Вы отдаёте [товар] → хотите получить [желаемый]».
- Список кандидатных цепочек (`GET /exchange-requests/{requestId}/chains`, статус `CANDIDATE`), отсортированных по убыванию `score`.
- **Карточка цепочки** содержит:
  - Визуализацию цепочки (аватары участников, стрелки, миниатюры товаров).
  - Длину (например, «3 участника»).
  - `score` как индикатор вероятности успеха (цветовой индикатор + процент, `score * 100`).
  - Кнопку «Выбрать эту цепочку» — видна только если `viewerPermissions.canSelect === true`; по нажатию — `POST /chains/{chainId}/select`, переход в `PROPOSED`.
- Пустое состояние: «Пока нет подходящих цепочек. Попробуйте изменить запрос позже».
- Также доступен общий список цепочек пользователя вне контекста конкретного запроса (`GET /chains`, `?status=CANDIDATE` / `?status=PROPOSED,FROZEN,IN_PROGRESS`) — отдельный экран не специфицирован в текущем MVP, зарезервирован под будущий UI «Мои сделки».

**Экран детали цепочки** (`/chains/:chainId`)

- Полная карточка цепочки (`GET /chains/{chainId}`): участники (кто что отдаёт/получает), статус, `viewerPermissions` — источник правды для того, какие действия показывать; frontend не дублирует бизнес-логику статусов.
- **`PROPOSED`**: каждый участник принимает или отклоняет своё участие (`POST /chains/{chainId}/responses/accept|decline`, доступно при `canRespond`); экран показывает статусы откликов остальных участников (`GET /chains/{chainId}/responses`).
- После последнего `ACCEPTED`-отклика (`isReadyForSelection: true`) начинается **мягкая блокировка**: участник подтверждает готовность (`POST /chains/{chainId}/freeze-votes/confirm`, доступно при `canVote`) до дедлайна (`freezeDeadlineAt`); после всех подтверждений цепочка сама переходит в `FROZEN`.
- Если участник отклоняет отклик/голос или не успевает до дедлайна (ошибка `410`) — доступна **замена участника**: список допустимых кандидатов (`GET /chains/{chainId}/replacement-candidates`, доступно при `canRequestReplacement`), выбор и приглашение замены, кандидат принимает или отклоняет приглашение.
- Удаление/отмена выбора — только через Modal-подтверждение (см. §2.8).
- Ошибки `409`/`410` — тост с сообщением и повторная загрузка карточки цепочки.

### 2.7. Профиль / Настройки

**Экран** `/profile`

- Отображение аватара, имени, email.
- Переключатель темы (светлая/тёмная).
- Смена пароля (`/profile/password`): поля «Текущий пароль», «Новый пароль» (мин. 8 символов), «Повторите новый пароль»; после успеха — экран «Пароль изменён» с возвратом в профиль.
- Кнопка «Выйти» – вызывает `POST /auth/logout`, затем удаляет JWT из `localStorage` и перенаправляет на `/login`.

### 2.8. Общие элементы интерфейса

- **Нижняя навигация** (мобильная): «Товары», «Запросы», «Профиль».
- **Боковое меню** (десктоп): аналогичные пункты + логотип.
- **Переключатель темы** на пре-авторизационных экранах и на странице профиля; в хедере/боковом меню его нет.
- **Иконка уведомлений** с бейджем количества непрочитанных — в хедере/боковом меню (см. §2.9).
- **Тосты** для уведомлений (успех, ошибка).
- **Модальные окна** для подтверждения опасных действий (удаление товара, отмена выбора цепочки).

### 2.9. Уведомления

**Список уведомлений** (открывается по клику на иконку из §2.8)

- Список уведомлений пользователя (`GET /notifications`), непрочитанные визуально выделены.
- Открытие/клик по уведомлению помечает его прочитанным (`POST /notifications/{notificationId}/read`).
- Кнопка «Прочитать все» (`POST /notifications/read-all`).
- Пустое состояние: «Уведомлений нет».
- Уведомления — только in-app; email/push-доставка вне рамок MVP (см. §1.3).

## 3. Архитектура приложения

### 3.1. Frontend (React + TypeScript)

- **Структура**: Feature-Sliced Design (FSD)
  - `app/` – провайдеры, роутинг, глобальные стили.
  - `pages/` – страницы (экраны).
  - `features/` – пользовательские сценарии (например, создание товара, создание запроса).
  - `entities/` – бизнес-сущности (товар, запрос, пользователь).
  - `shared/` – переиспользуемые UI-компоненты, утилиты, API-клиент.
- **Стек**:
  - React 18+
  - TypeScript
  - Ant Design (UI-kit)
  - Redux Toolkit (глобальное состояние: пользователь, тема)
  - TanStack Query (работа с API, кеширование)
  - Vite (сборка)
  - ESLint + Prettier (форматирование)
- **Управление авторизацией**: JWT хранится в `localStorage`. При каждом запросе токен добавляется в заголовок `Authorization: Bearer <token>`. При старте приложения (обновление страницы) текущий пользователь восстанавливается запросом `GET /auth/me`, если токен есть в `localStorage`.

### 3.2. Backend (Golang)

- **Язык**: Go (Golang)
- **База данных**: PostgreSQL.
- **API**: RESTful с JSON-ответами.
- **Маршруты** (см. раздел 4).
- **Аутентификация**: JWT-токены, время жизни токена — 24 часа.
- **Защита**: все эндпоинты, кроме регистрации и входа, требуют валидный JWT.
- **Мокирование на этапе фронтенд-разработки**: до готовности бэкенда фронтенд работает с мок-сервером (`json-server` на фикстурах, повторяющих контракты раздела 4). Мок-сервер живёт в `frontend/mock/` (`server.js` + фикстуры `db.json`, `passwords.json`), запускается через `npm run mock` и слушает `http://localhost:4000` (`VITE_API_BASE_URL` в `.env.development`). После интеграции с реальным API мок-сервер не используется.

### 3.3. DevOps

- **Контейнеризация**: Docker Compose, поднимающий:
  - Frontend (сборка через Vite, статика или dev-сервер)
  - Backend (Go-сервер)
  - База данных (PostgreSQL)
- **Переменные окружения**: порты, секреты (JWT-ключ, строки подключения).

### 3.4. Принципы разработки

_Частично основано на инженерных принципах Avito Playbook ([development-principles.md](https://github.com/avito-tech/playbook/blob/master/development-principles.md))._

- Бизнес-логика реализуется в коде бэкенда, не на стороне БД: без хранимых процедур и триггеров с бизнес-правилами. В PostgreSQL — данные и ограничения целостности (constraints, foreign keys).
- У каждой сущности — один источник правды в БД. Клиент не хранит собственных копий серверных данных, которые могут разойтись с сервером; кеш TanStack Query — временный и инвалидируется после мутаций.
- Миграции обратно совместимы: во время раскатки старая и новая версия бэкенда должны одинаково работать с текущей схемой БД (сначала совместимая миграция, потом код, который на неё опирается).
- Изменение считается готовым, когда оно покрыто тестом или проверено вручную по сценарию из `PROJECT.md`; непротестированное изменение не мёржится.
- Неиспользуемый код, эндпоинты и поля моделей удаляются сразу, а не остаются «на будущее».

## 4. API (эндпоинты)

Согласованный контракт с бэкендом (источник: `API-frontend.md`, актуализировано 2026-08-06). Черновой REST-контракт — детали (справочник категорий, точные enum'ы, разбивка ответов) уточняются по ходу интеграции. Все эндпоинты возвращают JSON. Все эндпоинты, кроме `/auth/register`, `/auth/login` и восстановления пароля (§4.1), требуют авторизации (`Authorization: Bearer <token>`). Frontend не считает граф, score, кластеры или дедлайны сам — получает готовое состояние от backend.

### 4.1. Аутентификация и пользователи

| Метод | Эндпоинт                       | Описание                                                                | Тело запроса                                                                             | Ответ (успех)                                  |
| ----- | ------------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------- |
| POST  | `/api/v1/auth/register`        | Регистрация и создание сессии (не защищён)                              | `{"fullName":"string","email":"string","password":"string"}`                             | `{"token":"jwt","user":{...}}`                 |
| POST  | `/api/v1/auth/login`           | Вход (не защищён)                                                       | `{"email":"string","password":"string"}`                                                 | `{"token":"jwt","user":{...}}`                 |
| POST  | `/api/v1/auth/logout`          | Завершить текущую сессию                                                | –                                                                                        | `{"message":"logged_out"}`                     |
| GET   | `/api/v1/auth/me`              | Текущий пользователь (используется для восстановления сессии, см. §3.1) | –                                                                                        | `{"id":"uuid","fullName":"...","email":"..."}` |
| POST  | `/api/v1/auth/change-password` | Смена пароля авторизованного пользователя                               | `{"currentPassword":"string","newPassword":"string","newPasswordConfirmation":"string"}` | `{"message":"password_changed"}`               |

Конкретные коды/сообщения ошибок входа и смены пароля определяются бэкендом; frontend ориентируется на общий формат ошибок (§4.9) — как минимум `401` для неверных данных входа, `400`/`422` для ошибки смены пароля.

**Восстановление пароля** — код из 6 цифр на email, три шага (запрос кода → проверка кода → установка пароля). Все три эндпоинта не защищены:

| Метод | Эндпоинт                                            | Описание                                 | Тело запроса                                             | Ответ (успех)                    |
| ----- | --------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------- | -------------------------------- |
| POST  | `/api/v1/account/password-recovery/send-code/`      | Отправить код восстановления на email    | `{"email":"string"}`                                     | `{"message":"code_sent"}`        |
| POST  | `/api/v1/account/password-recovery/verify-code/`    | Проверить код перед вводом нового пароля | `{"email":"string","code":"string"}`                     | `{"message":"code_valid"}`       |
| POST  | `/api/v1/account/password-recovery/reset-password/` | Установить новый пароль по коду          | `{"email":"string","code":"string","password":"string"}` | `{"message":"password_changed"}` |

Код живёт 10 минут и гасится после успешного сброса. Ошибки: `404` — email не зарегистрирован, `400` — неверный или истёкший код либо пароль короче 8 символов. Экранам этого флоу соответствует `DESIGN.md` §4.1 (`/forgot-password`, `RecoveryFlow.tsx`).

Черновик `API-frontend.md` описывает восстановление иначе — `/auth/forgot-password` + `/auth/reset-password` с одноразовым токеном из письма, без шага проверки кода и с полем `newPasswordConfirmation`. Согласовано, что бэкенд приводит ручки к варианту выше (код + отдельная проверка), а фронтенд и мок остаются как есть.

В моке (`frontend/mock/server.js`) `send-code` дополнительно возвращает поле `code` и печатает его в консоль — эмейл-доставки нет, иначе флоу не пройти вручную. В реальном API этого поля быть не должно.

Сессия — JWT в заголовке `Authorization: Bearer <token>`. Выход теперь выполняется и на бэкенде (`POST /auth/logout`), и на клиенте (токен удаляется из `localStorage`).

### 4.2. Товары (`items`)

Эндпоинт переименован с `/products` на `/items`; модель товара расширена категорией, состоянием, цветом, материалом и атрибутами, зависящими от категории. Статус товара: `ACTIVE` / `RESERVED` / `EXCHANGED`. В моке также есть `GET /api/v1/categories` (статичный каталог, вне согласованного контракта).

| Метод  | Эндпоинт                 | Описание                  | Тело запроса | Ответ (успех)                                      |
| ------ | ------------------------ | ------------------------- | ------------ | -------------------------------------------------- |
| GET    | `/api/v1/items`          | Мои товары                | –            | `[{"id":"uuid","title":"...", ...}]`               |
| POST   | `/api/v1/items`          | Создать товар             | см. ниже     | `{"id":"uuid", ...}`                               |
| GET    | `/api/v1/items/{itemId}` | Получить товар            | –            | `{"id":"uuid", ...}`                               |
| PATCH  | `/api/v1/items/{itemId}` | Изменить товар (частично) | см. ниже     | `{"id":"uuid", ...}`                               |
| DELETE | `/api/v1/items/{itemId}` | Архивировать товар        | –            | `{"message":"archived"}`                           |
| GET    | `/api/v1/categories`     | Каталог категорий (мок)   | –            | `[{"id":"electronics","name":"Электроника"}, ...]` |

Тело создания/изменения:

```json
{
  "title": "PlayStation 5",
  "description": "Консоль в хорошем состоянии, полный комплект",
  "categoryId": "electronics",
  "condition": "USED",
  "color": "white",
  "material": null,
  "attributes": {
    "storageGb": 825,
    "hasBox": true
  }
}
```

- `categoryId` — категория из каталога бэкенда (справочник категорий не входит в этот контракт — уточнить отдельный эндпоинт получения списка).
- `condition` — состояние товара (в UI используются значения «Новый», «Как новый», «Б/у», «Требует ремонта», см. §2.3; точный enum на бэкенде — уточнить, контракт даёт только пример `"USED"`).
- `color`, `material` — необязательные, `material` может быть `null`.
- `attributes` — специфичные для категории поля (например, `storageGb`/`hasBox` для электроники); набор полей зависит от `categoryId`.
- `embedding` frontend не передаёт — backend создаёт его сам.

### 4.3. Заявки на обмен

| Метод  | Эндпоинт                                       | Описание                                                                                                                                   | Тело запроса                                           | Ответ (успех)           |
| ------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ | ----------------------- |
| GET    | `/api/v1/exchange-requests`                    | Мои заявки                                                                                                                                 | –                                                      | `[{"id":"uuid", ...}]`  |
| POST   | `/api/v1/exchange-requests`                    | Создать заявку и синхронно запустить matching                                                                                              | см. ниже                                               | см. ниже                |
| GET    | `/api/v1/exchange-requests/{requestId}`        | Детали заявки                                                                                                                              | –                                                      | `{"id":"uuid", ...}`    |
| PATCH  | `/api/v1/exchange-requests/{requestId}`        | Изменить заявку и пересчитать локальное окружение (только живая заявка: `ACTIVE`/`IN_PROPOSAL`; `LOCKED`/`DONE`/`REMOVED` — только чтение) | `{"wantedDescription":"string","wantedProfile":{...}}` | `{"id":"uuid", ...}`    |
| DELETE | `/api/v1/exchange-requests/{requestId}`        | Деактивировать заявку (мягкое удаление → `REMOVED`)                                                                                        | –                                                      | `{"message":"deleted"}` |
| GET    | `/api/v1/exchange-requests/{requestId}/chains` | Цепочки, где участвует заявка                                                                                                              | –                                                      | см. §4.4                |

Тело создания:

```json
{
  "offeredItemId": "item_uuid",
  "wantedDescription": "Ищу ноутбук для программирования, желательно 16 ГБ RAM",
  "wantedProfile": {
    "categoryId": "laptops",
    "minRamGb": 16,
    "acceptableCondition": ["NEW", "USED"]
  }
}
```

- `wantedDescription` — обязательное свободное описание желаемого (заменяет прежние отдельные поля «название» + «описание»).
- `wantedProfile` — необязательный структурированный фильтр для мэтчинга: категория, допустимые состояния, специфичные для категории фильтры.

Ответ на `POST` (matching выполняется синхронно):

```json
{
  "request": { "id": "request_uuid", "status": "ACTIVE" },
  "matching": { "createdCandidateChains": 2 }
}
```

`matching.createdCandidateChains` — результат после сохранения (§2.4): если `> 0`, заявка переходит в `IN_PROPOSAL`; если `0` — остаётся в `ACTIVE` (в поиске).

Статус заявки: `ACTIVE` (в поиске) → `IN_PROPOSAL` (цепочки найдены/предложены) → `LOCKED` (выбрана цепочка, заявка защищена от редактирования) → `DONE` / `REMOVED` (терминальные). Выбор цепочки (`POST /chains/{chainId}/select`) переводит заявку в `LOCKED`.

### 4.4. Кандидатные цепочки

Цепочки больше не вложены только в заявку — доступны и как отдельный ресурс пользователя (`/chains`).

| Метод | Эндпоинт                                            | Описание                                       | Тело запроса | Ответ (успех)                             |
| ----- | --------------------------------------------------- | ---------------------------------------------- | ------------ | ----------------------------------------- |
| GET   | `/api/v1/chains`                                    | Все цепочки текущего пользователя              | –            | `[{...}]`                                 |
| GET   | `/api/v1/chains?status=CANDIDATE`                   | Только кандидаты                               | –            | `[{...}]`                                 |
| GET   | `/api/v1/chains?status=PROPOSED,FROZEN,IN_PROGRESS` | Активные сделки                                | –            | `[{...}]`                                 |
| GET   | `/api/v1/chains/{chainId}`                          | Детальная карточка цепочки                     | –            | см. ниже                                  |
| POST  | `/api/v1/chains/{chainId}/select`                   | Выбрать готовую цепочку и перейти в `PROPOSED` | –            | `{"id":"chain_uuid","status":"PROPOSED"}` |

Ответ `GET /chains/{chainId}` (должен быть удобен frontend'у):

```json
{
  "id": "chain_uuid",
  "status": "CANDIDATE",
  "score": 0.84,
  "freezeDeadlineAt": null,
  "participants": [
    {
      "position": 1,
      "requestId": "request_1",
      "isCurrentUser": true,
      "offeredItem": { "id": "item_1", "title": "PlayStation 5" },
      "receivesFromPosition": 3,
      "responseStatus": "ACCEPTED",
      "freezeVoteStatus": null
    }
  ],
  "viewerPermissions": {
    "canRespond": true,
    "canSelect": false,
    "canVote": false,
    "canRequestReplacement": false
  }
}
```

- `score` (0–1) заменяет прежний `successProbability` (0–100) — при отображении индикатора конвертировать в проценты (`score * 100`).
- `viewerPermissions` важен: frontend не дублирует бизнес-логику статусов цепочки, а лишь показывает/скрывает действия по этим флагам.
- Прежнее булево поле `selected` заменено на `status` (`CANDIDATE`/`PROPOSED`/`FROZEN`/`IN_PROGRESS`/...).

### 4.5. Отклики на `CANDIDATE`

| Метод | Эндпоинт                                     | Описание                    | Тело запроса | Ответ (успех)                                  |
| ----- | -------------------------------------------- | --------------------------- | ------------ | ---------------------------------------------- |
| POST  | `/api/v1/chains/{chainId}/responses/accept`  | Принять цепочку             | –            | `{"chainId":"...","status":"..."}`             |
| POST  | `/api/v1/chains/{chainId}/responses/decline` | Отклонить цепочку           | –            | `{"chainId":"...","status":"..."}`             |
| GET   | `/api/v1/chains/{chainId}/responses`         | Статусы откликов участников | –            | `[{"requestId":"...","responseStatus":"..."}]` |

После последнего `ACCEPTED` backend возвращает признак, что цепочка готова к выбору:

```json
{ "chainId": "chain_uuid", "status": "CANDIDATE", "isReadyForSelection": true }
```

### 4.6. Подтверждение мягкой блокировки

| Метод | Эндпоинт                                        | Описание            | Тело запроса | Ответ (успех) |

### 4.7. Замена участника

| Метод | Эндпоинт                                                             | Описание                       | Тело запроса | Ответ (успех)            |
| ----- | -------------------------------------------------------------------- | ------------------------------ | ------------ | ------------------------ |
| GET   | `/api/v1/chains/{chainId}/replacement-candidates`                    | Получить допустимые замены     | –            | `[{...}]`                |
| POST  | `/api/v1/chains/{chainId}/replacement-candidates/{requestId}/select` | Выбрать и пригласить замену    | –            | `{"message":"invited"}`  |
| POST  | `/api/v1/chains/{chainId}/replacement-invitation/accept`             | Кандидат принимает приглашение | –            | `{"message":"accepted"}` |

В список replacement candidates попадают уже отфильтрованные backend'ом заявки: участники псевдокластера, совместимые с предыдущим и следующим звеном цепи, активные и без резервирования.

### 4.9. Общие ошибки

| Код | Когда показывать                                         |
| --- | -------------------------------------------------------- |
| 401 | Сессия истекла — отправить на `/login`                   |
| 403 | Пользователь не участник цепочки / не владелец ресурса   |
| 404 | Ресурс отсутствует или недоступен                        |
| 409 | Конфликт: товар уже в резерве, цепочка успела измениться |
| 410 | Deadline истёк, цепочка откатилась                       |
| 422 | Ошибка валидации полей                                   |

Для `409` и `410` frontend лучше показывает сообщение и повторно загружает карточку цепочки.

## 7. Требования к бэкенду

### 7.1. База данных

- PostgreSQL: структурированная схема, транзакции, целостность данных на уровне БД.
- Схема: пользователи, товары (items), запросы, цепочки, уведомления (см. модели ниже).
- Миграции – с использованием `golang-migrate`.

### 7.2. Модели данных (сущности)

- **User**: id, full_name, email, password_hash, created_at.
- **Item** (ранее Product, эндпоинт `/items`): id, user_id, title, description, category_id, condition, color, material (nullable), attributes (jsonb, зависят от category_id), image_url, embedding (вычисляется бэкендом), status (ACTIVE, RESERVED, EXCHANGED), created_at, updated_at.
- **ExchangeRequest**: id, user_id, offered_item_id, wanted_description, wanted_profile (jsonb, необязательный структурированный фильтр — category_id/acceptable_condition/доп. атрибуты), status (ACTIVE, IN_PROPOSAL, LOCKED, DONE, REMOVED), created_at, updated_at.
- **Chain**: id, status (CANDIDATE, PROPOSED, FROZEN, IN_PROGRESS, ...), score (0–1), freeze_deadline_at, participants (JSON: position, request_id, offered_item, receives_from_position, response_status, freeze_vote_status), created_at. Кандидатные цепочки генерируются matching-алгоритмом синхронно при создании заявки (§4.3); дальнейшие переходы статуса — по действиям участников: отклики (§4.5), freeze-votes (§4.6), замена участника (§4.7).
- **Notification**: id, user_id, text, read (bool), created_at.

### 7.3. Обработка ошибок

- Единый формат ошибок: `{"error": "message", "code": 400}`.
- Структурированное логирование ошибок на уровне приложения.

### 7.4. Деплой

- Dockerfile для бэкенда (многоступенчатая сборка).
- Docker Compose для подъёма всех сервисов (фронт, бэк, БД).
