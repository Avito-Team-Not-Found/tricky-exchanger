# DESIGN.md — Спецификация дизайна сервиса многостороннего бартера (MVP)

Дизайн-система и постраничная спецификация для прямой разработки в коде. Источник истины по всем визуальным и интерактивным решениям фронтенда — этот документ; соответствие бизнес-сценариям см. в `PROJECT.md`.

### 1.2. Цвет — тёмная тема

| Токен                    | Значение  | Назначение                   |
| ------------------------ | --------- | ---------------------------- |

| `--color-bg-card`        | `#1F1F1F` | Фон карточек                 |
| `--color-text-primary`   | `#FFFFFF` | Основной текст (18.5:1)      |

| `--color-status-success` | `#52C41A` | Успех (12.5:1)               |
| `--color-status-warning` | `#FAAD14` | Предупреждение (9.0:1)       |
| `--color-status-error`   | `#FF4D4F` | Ошибка (10.8:1)              |
| `--color-border-default` | `#3A3A3A` | Границы, разделители         |

Оба набора реализуются как одна пара CSS custom properties, переключаемая атрибутом `data-theme` на корне документа:

```css
:root[data-theme='light'] {
  --color-bg-page: #ffffff; /* ... */
}
:root[data-theme='dark'] {
  --color-bg-page: #141414; /* ... */
}
```

Переход между темами анимируется на затрагиваемых свойствах: `transition: background-color .2s ease, color .2s ease, border-color .2s ease`.

### 1.3. Индикация вероятности успеха цепочки

| Уровень | Цвет                     | Обязательно текстом |
| ------- | ------------------------ | ------------------- |
| Высокая | `--color-status-success` | «Высокая» + `NN%`   |
| Средняя | `--color-status-warning` | «Средняя» + `NN%`   |
| Низкая  | `--color-status-error`   | «Низкая» + `NN%`    |

Цвет никогда не единственный носитель информации — уровень всегда продублирован словом и числом
(в Penpot бейдж вероятности идёт без иконки: текст «Средняя · 72%» на тонированной заливке).

### 1.7. Брейкпоинты и контейнер

Три брейкпоинта: **375px (mobile) / 768px (tablet) / 1024px+ (desktop)**. Разметка — одна адаптивная структура на все три, без отдельных макетов. Десктопный контейнер — `max-width: 1200px`, центрирован.

### 1.8. Доступность (сквозные правила)

- Контраст текста ≥ 4.5:1 (≥3:1 для крупного текста от 18px/24px+).
- Минимальный размер интерактивных элементов — **44×44px**.
- У каждого интерактивного элемента — видимый **focus-ring** (например, `outline: 2px solid var(--color-accent-primary); outline-offset: 2px`), не убирать `outline` без замены.
- Состояние (успех/ошибка/предупреждение) всегда дублируется иконкой и/или текстом, не только цветом.

### 1.9. Тема Ant Design (ConfigProvider)

UI-кит — **Ant Design (antd) 6**. Фирменный акцент Авито — синий, поэтому здесь не вводится отдельная брендовая палитра: токены `token.colorPrimary` и т.д. — это прямая проекция таблиц §1.1/1.2 на API `ConfigProvider`, один в один с тем, что уже нарисовано в макете авторизации в Penpot (`AuthCard`, `Segmented`, `InputBox`, `Button / primary / large`).

Реализация темы — `src/app/providers/ThemeProvider.tsx`, она же источник истины по конкретным
значениям `ThemeConfig`; здесь фиксируются только требования к ней:

- палитра, радиусы и шрифт — из §1.1/1.2/1.4/1.5, теми же значениями, что и в `tokens.scss`;
- высоты контролов: `controlHeight` 44, `controlHeightLG` 52 (§2.1); размер текста кнопок и полей ввода — 16px (§1.4), antd по умолчанию рисует 14px;
- `colorBgContainer` — фон полей и карточек, `colorBgElevated` — приподнятые поверхности (`AuthCard`); перепутанные местами, они гасят контраст поля на фоне карточки;
- у `Segmented` трек и активный сегмент задаются явно: значения antd по умолчанию сливают активный таб с карточкой;
- элевация в тёмной теме — через `colorBgElevated`, тень не рисуется (§1.6).

Переключение темы — оборачивание приложения в `<ConfigProvider theme={isDark ? darkTheme : lightTheme}>` по значению атрибута `data-theme` (§1.2), а не через CSS-only переключение: значения `colorPrimary`/`colorSuccess`/`colorWarning`/`colorError` намеренно одинаковы в обеих темах (см. контраст в §1.1/1.2), меняются только фон, текст и граница.

Компоненты §2, у которых нет прямого соответствия в antd (`StatusTag` — пилюля с заливкой статус-цвета и белым текстом, `ProbabilityBadge`, `ChainCard`, `ChainDetail`, `Avatar`-фолбэк с инициалами) — не берутся из коробки antd `Tag`/`Badge`, а собираются как обёртки поверх токенов темы (`token.colorSuccess` и т.д. через `theme.useToken()`), чтобы сохранить контраст и обязательное дублирование текстом из §1.3.

### 1.10. Движение

Длительности и кривые — только токенами из `src/app/styles/tokens.scss`, без хардкода `0.2s ease` по файлам:

| Токен                     | Значение                     | Где применяется                                                 |
| ------------------------- | ---------------------------- | --------------------------------------------------------------- |
| `--motion-duration-fast`  | `120ms`                      | микро-отклик: `:active` карточки, фокус-рамка                   |
| `--motion-duration-base`  | `200ms`                      | появление элемента, шаг флоу, переход экрана на десктопе (fade) |
| `--motion-duration-slow`  | `280ms`                      | переход экрана на мобильном (slide)                             |
| `--motion-ease-standard`  | `cubic-bezier(0.2, 0, 0, 1)` | по умолчанию, в том числе для смены цвета                       |
| `--motion-ease-out`       | `cubic-bezier(0, 0, 0, 1)`   | появление элемента                                              |
| `--motion-slide-distance` | `16px`                       | сдвиг для slide/rise-анимаций экранов и списков                 |

Переиспользуемые `@keyframes` и утилитарные классы живут в `src/app/styles/motion.scss`: `motion-fade-in`, `motion-rise-in`, `motion-slide-in-right`, `motion-slide-in-left`, `motion-pop-in` и классы `.motion-screen` (переход экрана), `.motion-step` (шаг пошагового флоу), `.motion-cascade` (каскадное появление детей списка или сетки — задержка по позиции ребёнка, дальше 6-го не растёт).

Сквозные правила:

- **Анимируются только `transform` и `opacity`.** Они не вызывают пересчёт layout, поэтому движение не дёргает соседние элементы. `height`/`width`/`top` не анимируются.
- **`prefers-reduced-motion: reduce` отключает движение полностью** — это требование доступности, а не опция. CSS-анимации гасит правило в `global.scss`, JS-анимации компонентов antd (`CSSMotion` у `Modal`/`Drawer`) — seed-токен `motion: false` в `ThemeProvider` (хук `useReducedMotion`).
- **Своё движение не кладётся поверх готового antd.** Открытие/закрытие модалок, шиммер `Skeleton`, `wave` кнопок и тосты — движение antd; собственных анимаций для них нет.
- **Анимация появления не повторяется при рефетче**: ключи элементов списков стабильны, узлы не перемонтируются. Там, где перезапуск нужен осознанно (бейдж согласий, пилюля статуса доставки, шаг флоу), он делается сменой `key`.

## 2. Библиотека компонентов

Для каждого компонента: варианты, состояния (`default / hover / active / focus / disabled`), обязательные пропсы.

### 2.1. Button

- Варианты: `primary` (заливка accent, белый текст), `secondary` (обводка `border-default`, текст `text-primary`), `danger` (заливка `status-error`, для «Отозвать отклик»/«Удалить»), `ghost` (без фона/обводки, используется как второстепенное действие).
- Размеры: `medium` (высота 44px), `large` (высота 52px, десктоп/основные CTA).
- Состояния: `default`, `hover` (затемнение/осветление фона на 8%), `active` (ещё на 8%), `disabled` (opacity 0.4, курсор not-allowed, без hover/active), `loading` (спиннер вместо текста или рядом, кнопка неактивна).
- Focus-ring обязателен на всех вариантах.

### 2.2. Input / Textarea / Select

- Состояния: `default`, `focus` (обводка accent + focus-ring), `error` (обводка `status-error`, текст ошибки под полем с иконкой), `disabled` (фон `bg-card`, текст `text-secondary`, opacity).
- Textarea — как Input, но `min-height` под несколько строк, счётчик символов справа снизу (`120/500`), обязателен при лимите.
- Select — выпадающий список, значок шеврона, список опций с тем же радиусом/тенью, что и карточки.
- Label всегда снаружи поля сверху; обязательные поля помечены `*`.
- Вертикальный ритм форм — единый на всех экранах-формах: между полями `--spacing-lg` (24px), от последнего поля до основной кнопки 32px, между основной и danger-кнопкой `--spacing-md` (16px), от заголовка блока до содержимого `--spacing-md`. Отступы задаются одним источником (antd-отступ `Form.Item`), а не flex-gap контейнера поверх него — иначе они складываются.

### 2.3. Checkbox / Radio

- Для выбора отдаваемого товара в форме запроса используется Radio (одиночный выбор).
- Размер тач-таргета — 44×44px даже если визуальный квадрат/круг меньше (расширяется padding).
- Группа чекбоксов в строку переносится на узких экранах: интервал между строками — `--spacing-md` (antd задаёт только горизонтальный зазор).

### 2.4. Тег статуса (StatusTag)

Пилюля (radius-full), залитая статус-цветом полностью, текст — белый (соответствует макету в Penpot). Нейтральный статус («Завершён», «Зарезервирован») — фиксированный серый `#595959`, чтобы белый текст не терял контраст в тёмной теме.

Подпись «Зарезервирован» встречается у обеих сущностей, но тон у них разный: у заявки это
терминальное для правки состояние (нейтральный), у товара — временная недоступность (warning).

| Сущность | Статус (`PROJECT.md` §4.3, §4.2) | Подпись        | Цвет                         |
| -------- | -------------------------------- | -------------- | ---------------------------- |
| Заявка   | `ACTIVE`                         | Активен        | success                      |
| Заявка   | `IN_PROPOSAL`                    | В процессе     | warning                      |
| Заявка   | `LOCKED`                         | Зарезервирован | text-secondary (нейтральный) |
| Заявка   | `DONE`                           | Завершён       | text-secondary (нейтральный) |
| Заявка   | `IN_PROGRESS`                    | Выполняется    | text-secondary (нейтральный) |
| Товар    | `ACTIVE`                         | Активен        | success                      |
| Товар    | `UNAVAILABLE`                    | Зарезервирован | warning                      |
| Товар    | `ARCHIVED`                       | В архиве       | text-secondary (нейтральный) |

`REMOVED` сервер отфильтровывает из списка и детали заявок, поэтому тега «Отменён» в UI нет.

### 2.5. ProbabilityBadge

Пилюля (высота 26, radius-full, padding `0 8`) с заливкой уровня в 15% прозрачности; внутри —
Caption «Уровень · `NN%`» цветом уровня по таблице §1.3. Используется в карточке цепочки и в
шапке деталей цепочки.

### 2.6. ProductCard

- Единый блок-карточка: фон `bg-card`, radius-md, `overflow: hidden`; фото (1:1, `object-fit: cover`) и название внутри одного блока.
- Название (Body, 1 строка, truncate), StatusTag поверх фото (top-left).
- Кнопок на карточке нет (убраны по решению продукта): тап по карточке открывает экран редактирования товара (§4.3), архивирование — на этом экране.
- Сетка: 2 колонки на 375px, 3 на 768px, 4 на 1024px+, gap = `--spacing-md`.

### 2.7. ChainCard (карточка варианта обмена в списке)

- Карточка: фон `bg-card`, radius-md, padding `--spacing-md`, вертикальный ритм `--spacing-md`, без рамки.
- Фото получаемого товара — крупный блок (пропорция 311:171, radius-md) в верхней части карточки, без рамки; без фото — заглушка с первой буквой названия.
- Название товара (Subtitle) и вторая строка Caption `text-secondary` «Хочет: [что хочет взамен]» — кандидат отдаёт этот товар и хочет получить твой.
- Длина цепочки текстом («3 участника») из `length` ответа (§3.4), ProbabilityBadge (`score * 100`, §1.3); у собранной цепочки (`PROPOSED` и дальше) место бейджа занимает пилюля «Цепочка собрана» в тоне `status-success`.
- **Действие.** Какая кнопка доступна при каком статусе цепочки и какой запрос она шлёт — `PROJECT.md` §2.6; здесь только оформление:
  - `CANDIDATE` — «Откликнуться» — `primary` block; «Отозвать отклик» — `danger` block (Modal-подтверждение, §2.11).
  - `PROPOSED` — рамка 2px `status-success`, «Требуются действия» — `primary` block; в модалке «Готовность к сделке» (§6.1) «Отказ» — `text` тона `status-error`. После моего подтверждения кнопку заменяет статусная пилюля тона `success` «Вы подтвердили · ждём остальных», рамка выделения снимается.
  - `PROPOSED` с вакансией (непустой пул замен) — та же рамка `status-success`, но «Требуется действие» — `primary` block, ведёт на экран замены (§4.7).
  - `FROZEN` — рамка `status-success`, «Требуется действие» — `primary` block; `IN_PROGRESS`/`COMPLETED` — рамка `status-success`, «Перейти к сделке» — block в тоне `status-success`.
  - Недоступная карточка (по одной из цепочек запроса уже идёт согласование) — `opacity: .5`, `pointer-events: none`, `aria-disabled`; причину при `FROZEN` объясняет баннер над списком (§4.6).
- Бейдж «N/M согласий» у собранных цепочек — пилюля сплошной заливки `accent-primary`, белый текст, Caption 600.
- Таймер дедлайна цепочки (`TimerRow`, макет 4.6) — между мета-строкой и блоком действий, при непустом `freezeDeadlineAt`: пилюля во всю ширину, padding 8px 12px, gap 8px, radius-md, заливка `status-warning` на 12%, иконка «⏱» 16px и текст (Body Small 600, цвет `status-warning`). Текст — «Осталось 47 ч 58 мин на ответ» (`PROPOSED`), «… на отправку» (`FROZEN`) или «… на замену» (`PROPOSED` после отказа на `FROZEN`, быстрая замена — `PROJECT.md` §4.8). Строка тикает локально раз в 30 с; ровное число часов — «Осталось 1 ч на ответ» (без «0 мин»), меньше часа — «Осталось 58 мин на ответ», меньше минуты — «Осталось меньше минуты на ответ». Таймер не взаимоисключает бейдж «N/M согласий» и остаётся видимым после моего «Да» — дедлайн общий для цепочки. Откуда берётся дедлайн и что происходит по его истечении — `PROJECT.md` §4.6.
- Тап по карточке открывает детальный экран цепочки (`/chains/:id`); у приглушённой карточки тап не работает.

### 2.8. ChainDetail (экран цепочки: товар и участники)

Детали цепочки делятся на два экрана (макеты 4.7 и 4.8).

**Экран товара** (`/chains/:chainId`, макет 4.7):

- Заголовок — название получаемого товара, кнопка «Назад» (на список вариантов запроса).
- Крупное фото получаемого товара (343×280, radius-md), название, «N участников в цепочке» (`length`), ProbabilityBadge (`score * 100`, §1.3); у собранной цепочки место бейджа занимает пилюля «Цепочка собрана» в тоне `status-success` (та же стилистика, что у остальных таких бейджей), прижата к правому краю мета-строки.
- Пока цепочка `CANDIDATE`, получаемое звено — пул кандидатов (§3.1): если кандидат не один, заголовок показывает «Получаете: N вариантов», «Описание» не выводится. У собранной цепочки кандидат один — показываются его товар и описание.
- «Описание» — текст из `participants[].offeredItemDescription`.
- Таймер дедлайна ответа (`TimerRow`, макет 4.7) — между шапкой и «Описанием», при `PROPOSED` и непустом `freezeDeadlineAt`: та же пилюля, что в §2.7. Таймер и плашка жёсткой блокировки взаимоисключащи (`PROPOSED` против `FROZEN`).
- Кнопка `secondary` large «Посмотреть всю цепочку» → `/chains/:chainId/participants`. На `CANDIDATE` внизу — отклик той же стилистики, что на карточке списка (§2.7), в размере large block; на какого кандидата он действует — `PROJECT.md` §2.6.
- На `FROZEN` внизу, под «Требуется действие», — второстепенная кнопка «Отказаться от сделки» (`text`, `danger`, large block) → модалка отказа (§2.11). После подтверждения/заморозки успех-тост дополняется «. Письмо придёт на почту» — о статусе обмена бэкенд пишет на почту (§2.10).
- Если `GET /chains/:id` вернул `410` (дедлайн истёк, цепочку откатил сервер именно для этого пользователя) — вместо экрана `EmptyState` «Время истёкло / Дедлайн цепочки прошёл, обмен распался» с CTA-кнопкой `primary` «К моим запросам» (§2.13).

**Экран участников** (`/chains/:chainId/participants`, макет 4.8):

Вертикальный (моб.) / горизонтальный (дескт.) список строк-звеньев кольца: Аватар → Псевдоним по позиции (§2.9). Строка текущего пользователя — подложка `bg-card` и рамка 2px `accent-primary`, остальные строки без подложки и рамки. Строки идут с шагом `--spacing-md`, padding строки — `--spacing-md`, radius-md.

Внутри звена — пул кандидатов его кластера:

- один кандидат → мини-карточка товара: миниатюра 28×28 radius-sm, название (Caption `text-primary`), «Хочет: ...» (Caption `text-secondary`);
- несколько кандидатов на **не** получаемом звене → свёрнутая пилюля-счётчик «N вариантов» (фон `bg-card`, Caption `text-secondary`);
- несколько кандидатов на **получаемом** звене → список таких мини-карточек со статусом отклика каждой; отклик выполняется на экране товара цепочки и на карточке списка, здесь не дублируется.

Статус отклика кандидата (только на получаемом звене) — пилюля radius-full с 15%-й заливкой тона и Caption (600) того же цвета, сразу за карточкой товара. Подпись текстом обязательна — статус не передаётся одним лишь цветом.

| Статус   | Индикатор                 |
| -------- | ------------------------- |
| pending  | `warning` «Ожидаем»       |
| approved | `success` «Отклик принят» |
| rejected | `error` «Отклик отклонён» |
| нет      | —                         |

На `CANDIDATE` на этом экране действий отклика нет — они на карточке списка (§2.7) и на экране товара цепочки (§2.8). Когда бэкенд переводит цепочку в `PROPOSED` (`PROJECT.md` §4.5), показывается тост «Цепочка собрана».

Второй раунд на `PROPOSED` и дальше (какой голос откуда берётся — `PROJECT.md` §2.6):

- Над списком — пилюля «Цепочка собрана» (тон `success`, слева) и бейдж «N/M согласий» (§2.7).
- В шапке каждой строки-звена, сразу за псевдонимом, — пилюля голоса второго раунда участника: «Согласился» (`success`) / «Думает» (`warning`) / «Ожидает ответа» (`warning`) / «Отказался» (`error`) / «Место освободилось» (`neutral`, вакансия после отказа). Подпись текстом обязательна — статус не передаётся одним лишь цветом.
- Внизу экрана — действие по статусу цепочки, в размере large block: «Требуются действия» — `primary`, «Вы подтвердили · ждём остальных» — статусная строка, на вакансии (непустой пул замен) — «Требуется действие» — `primary`, «Перейти к сделке» — в тоне `status-success`.
- Пилюли отклика первого раунда («Ожидаем»/«Отклик принят»/«Отклик отклонён») на `PROPOSED` и дальше не показываются — словарь выбирается по статусу цепочки, а не по наличию `vote`.

Раскладка по брейкпоинтам (макет только мобильный, 768px+ — доработка):

- **до 768px**: строка звена — колонка (шапка, под ней пул кандидатов).
- **768px+**: строка звена — одна строка, «кто» слева, «что предлагает» справа; контент и шапка экрана выравниваются по общей колонке 640px, на 1024px+ — 800px (в 640px названия двух товаров в строке режутся уже на третьем слове).

⚠️ Бейдж «N/M» на `PROPOSED`-карточке списка (4.6) и дедлайн ответа считаются из детали
`GET /chains/{id}`: `approvedVotes` и `freezeDeadlineAt` в `exchange-options` не приходят
(`PROJECT.md` §4.6). Экрана «Я подумаю» нет: решение по собранной цепочке принимается только через
«Да»/«Отказ», голос `thinking` только отображается («Думает»).

### 2.9. Avatar и псевдонимы участников

Круг, размеры `sm` (24px, в мини-визуализации), `md` (40px, в списках), `lg` (64px, профиль). Фолбэк — инициалы на фоне `accent-primary` с 15% непрозрачностью.

**Анонимность участников цепочки (MVP).** Настоящие имена других участников не показываются нигде в интерфейсе цепочки — ни текстом, ни в `title`/`aria-label` аватара. Вместо имени — псевдоним-животное с эмодзи в аватаре (макет 4.8: 🐻 Мишка, 🦊 Лиса, 🐱 Кот; список продолжен до 12 животных). Эмодзи рисуется вполовину диаметра аватара (20px при `md`), подпись/инициалы — Body Small. Псевдоним выдаётся по позиции участника в цепочке, а не по id пользователя: позиции внутри цепочки уникальны, поэтому два участника одной цепочки никогда не получат одно животное. Текущий пользователь исключение — аватар «Я», подпись «Вы». Правило действует и в мини-визуализации ChainCard (§2.7), и на экране участников (§2.8).

### 2.10. Toast

Плавающий блок снизу (моб.) / сверху-справа (дескт.), radius-md, тень, иконка статуса + текст, автозакрытие через 3–4с, вариант `success` / `error` / `warning`.

Тосты статуса, которые дублируются письмом на почту, дополняются подсказкой: успех заморозки
цепочки — «Сделка подтверждена. Письмо придёт на почту», отказ по истечении дедлайна — `warning`
«Время истекло, цепочка распалась» (§4.6).

### 2.11. Modal (подтверждение)

Оверлей `rgba(0,0,0,0.5)`, карточка по центру, radius-lg, заголовок + текст вопроса + две кнопки (`secondary` «Отмена», `danger` «Да, удалить»). Используется для удаления товара, отзыва отклика цепочки и отказа от сделки («Отказаться от сделки?» → «Да, отказаться»).

### 2.12. Навигация

- **Mobile/Tablet (до 1023px)**: нижний таб-бар, 3 пункта — «Товары», «Запросы», «Профиль», высота 56–64px, активный пункт — иконка+подпись цвета accent, safe-area padding снизу.
- **Desktop (1024px+)**: боковое меню слева, фиксированная ширина ~240px, лого сверху, те же 3 пункта.
- Хедер (все брейкпоинты): название/лого, на главном экране — кнопка «+».
- **Экраны цепочки** (`/chains/:chainId`, `/chains/:chainId/participants`, макеты 4.7/4.8): своя шапка (56px, «Назад» + заголовок, разделитель 1px `border-default`), глобального хедера и таб-бара нет — низ мобильного экрана занимает кнопка действия. Боковое меню десктопа (1024px+) остаётся: там кнопка действия ничего не перекрывает, а макеты этих экранов только мобильные.

Переключатель темы есть только на пре-авторизационном экране (в правом верхнем углу, §4.1) и на странице профиля (§4.8) — в хедере и боковом меню его нет.

### 2.13. EmptyState

Иллюстрация (или крупная линейная иконка 96–120px) + заголовок (Subtitle) + описание (Body Small, `text-secondary`) + CTA-кнопка при необходимости. Тексты по экранам — см. §4.

### 2.14. Skeleton

Серые прямоугольники (`bg-card`, скруглённые под форму реального контента) с shimmer-анимацией (`background-position` keyframe, 1.2–1.5с), повторяют разметку карточек/списков на момент загрузки.

## 3. Навигация и общие взаимодействия

- Переходы между экранами — только на входе нового экрана: slide (мобильный, горизонтальный, `--motion-duration-slow`) или fade (десктоп, 1024px+, `--motion-duration-base`). Направление slide — по типу навигации: «Назад» въезжает слева, переход вперёд — справа. Выходной анимации у старого экрана нет: лейаут перемонтирует обёртку `<Outlet />` по `key={pathname}` при каждой навигации, поэтому старый экран снимается мгновенно (см. §1.10). Холодный старт не анимируется, чтобы первая страница не «въезжала» в кадр.
- Любое удаление и отзыв отклика цепочки — только через Modal-подтверждение, без исключений.
- Тосты — единый канал обратной связи для успеха/ошибки; не блокируют интерфейс.
- Валидация форм — inline, при сабмите фокус переводится на первое невалидное поле.

## 4. Экраны

Для каждого экрана: назначение, брейкпоинты (одна адаптивная структура, отличия отмечены), состояния.

### 4.1. Авторизация

- Способ входа: **email + пароль** (без соцсетей и SMS в MVP).
- Без хедера с логотипом-темой/таб-бара/бокового меню — отдельный, максимально простой пре-авторизационный layout: по центру экрана карточка формы (моб. — на всю ширину с отступами `--spacing-md`, дескт. — фиксированная ширина ~400px по центру), сверху — логотип/название приложения, тумблер темы — в правом верхнем углу экрана.
- Переключатель режима **«Войти» / «Зарегистрироваться»** — таб-переключатель (2 сегмента) над формой. Переключение сегмента — смена режима того же экрана (`/login` ↔ `/register`), а не навигация: screen-анимация перехода не проигрывается (см. §3).
- **Форма «Войти»**: Email (обяз., валидация формата), Пароль (обяз., маска с иконкой показать/скрыть), ссылка «Забыли пароль?» (Caption, под полем пароля, выровнена вправо), кнопка «Войти» (`primary`, `large`, на всю ширину, `disabled` до заполнения обоих полей).
- **Форма «Зарегистрироваться»**: Имя (обяз.), Email (обяз., валидация формата), Пароль (обяз., минимум 8 символов — подсказка Caption под полем), Повтор пароля (обяз., сверка со значением выше), кнопка «Зарегистрироваться» (`primary`, `large`, на всю ширину, `disabled` до валидности всех полей).
- Переключение между режимами — только таб-переключателем сверху; текст-ссылки под кнопкой не дублируются.
- **Ошибки валидации**: инлайн под каждым полем (см. §2.2), при входе: несуществующий email → Toast «Пользователь с таким email не найден», неверный пароль → Toast «Неверный пароль».
- **Ошибка сервера**: Toast «Не удалось подключиться. Повторите попытку» без потери введённых данных.
- **Loading**: кнопка сабмита → состояние `loading`, поля `disabled` на время запроса.
- Успех входа/регистрации → редирект на 4.2 (Главный экран).

**Восстановление пароля** (`/forgot-password`, без хедера/навигации, та же карточка и логотип, что у входа) — флоу из четырёх шагов, следующий шаг открывается после успеха текущего. В карточке сверху — кнопка «← Назад» (`ghost`/`text`) → переход на `/login`, скрыта на финальном шаге успеха:

1. **Email**: заголовок «Восстановление пароля», описание «Введите email, указанный при регистрации — мы отправим код для сброса пароля», поле Email (обяз., валидация формата), кнопка «Отправить код» (`primary`, `large`, `disabled` до валидности), внизу — «Вспомнили пароль? Войти».
2. **Код**: заголовок «Введите код», описание «Мы отправили 6-значный код на <email>», поле OTP на 6 цифр (один символ на бокс), ссылка «Не пришёл код? Отправить снова», кнопка «Подтвердить» (`primary`, `large`, `disabled` до заполнения 6 цифр).
3. **Новый пароль**: заголовок «Новый пароль», описание «Придумайте новый пароль для входа», поля «Новый пароль» (мин. 8 символов, подсказка Caption) и «Повторите пароль» (сверка), кнопка «Изменить пароль» (`primary`, `large`, `disabled` до валидности всех полей).
4. **Успех**: зелёная галочка, заголовок «Пароль изменён», описание «Используйте новый пароль при следующем входе», кнопка «Войти» (`primary`, `large`) → редирект на `/login`.

Ошибки: неизвестный email → Toast «Пользователь с таким email не найден», неверный/истёкший код → Toast «Неверный или истёкший код», сетевая ошибка → Toast «Не удалось подключиться. Повторите попытку». Loading и disabled — как у входа.

### 4.2. Главный экран — Товары

- **Хедер**: логотип/название, `+` (добавить товар).
- **Контент**: сетка ProductCard, 2/3/4 колонки по брейкпоинтам (§2.6).
- **Пустое состояние**: иллюстрация/иконка + «У вас пока нет товаров» + «Нажмите «+», чтобы добавить первый товар» + CTA-кнопка «Добавить товар» (соответствует макету «4.2 без товаров»).
- **Обрезание списка**: сервер отдаёт максимум 100 товаров; при большем общем количестве под сеткой — подпись «Показаны первые N из M товаров» (`color-text-secondary`).
- **Loading**: сетка Skeleton-карточек той же сетки.
- **Навигация**: активный пункт «Товары».

### 4.3. Создание/редактирование товара (форма)

- Хедер: «Назад» + «Новый товар» / «Редактирование товара» (`/products/new`, `/products/:id/edit`).
- Поле загрузки фото: широкая карточка (343×213, адаптивно по ширине, radius-md).
  - Без фото — сама карточка является триггером загрузки: пунктирная рамка + «Добавить фото» (клик открывает выбор файла).
  - С фото — карточка показывает фото, под ней единственная ghost-кнопка «Удалить фото» (кнопки замены нет: убрал фото → добавляй заново).
- **Фото обязательно в обеих формах**: у существующего товара без фото кнопку сохранения не активировать.
- Поля: Название (текст, ≤100, счётчик), Категория (`Select` с поиском, обязательная), Описание (textarea, ≥25 и ≤500, счётчик; короче 25 — ошибка «Пожалуйста, опишите товар подробнее», кнопка сохранения неактивна). Категория выбирается только из справочника (4 значения) — свободный ввод развёл бы взаимозаменяемые заявки по разным пулам кандидатов (см. `PROJECT.md` §2.3). Подсказки под полем нет — ни в форме товара, ни в форме заявки: обязательность видна по звёздочке, а объяснять роль категории пользователю нечем (она не ограничивает, с кем он меняется). Поля `color`/`material`/`attributes` в текущем UI отсутствуют — колонок в БД нет.
- Кнопка «Сохранить» (`primary`, `large`) — `disabled`, пока не заполнены все обязательные поля (при создании — ещё и без фото); при сабмите — `loading`, повторный сабмит заблокирован.
- Успех → Toast + редирект на 4.2.
- На 768/1024 — форма в 2 колонки (фото слева, поля справа) внутри контейнера max-width.

### 4.4. Создание/редактирование запроса на обмен

- Хедер: «Назад» + «Новый запрос» / «Редактирование запроса» (`/exchange-requests/new`, `/exchange-requests/:id/edit`).
- Блок «Что вы отдаёте?»: список собственных товаров с Radio — миниатюра фото (48×48, `radius-md`) + название; товары со статусом «недоступен» — недоступны для выбора (Radio `disabled` + подпись статуса), чужие товары в списке не появляются вовсе.
- Под списком — ghost-кнопка «+ Создать новый товар» (открывает 4.3, после сохранения возвращает сюда с выбором созданного товара); при отсутствии товаров кнопка остаётся единственным элементом блока.
- Блок «Что вы хотите получить?»: Категория (`Select` с поиском, обязательная, тот же справочник, что и в форме товара), «Что вы хотите получить» (textarea, обяз., ≥25 и ≤500, счётчик — тот же минимум, что у описания товара в 4.3; короче 25 — ошибка «Пожалуйста, опишите подробнее»).
- Кнопка «Создать запрос» — активна при выбранном отдаваемом товаре, выбранной категории и описании желаемого не короче 25 символов; при сабмите — `loading`, повторный сабмит заблокирован.
- Успех → экран результата: «Найдено N подходящих цепочек» (заявка в статусе «В процессе») или «Пока подходящих цепочек нет — заявка остаётся в поиске»; кнопка «К моим запросам».
- **Редактирование**: у заявок, созданных до правила 25 символов (бэкенд его не проверяет, `PROJECT.md` §4.3), короткое описание подсвечивается ошибкой сразу при открытии формы — иначе кнопка сохранения молча неактивна и отказ нечем объяснить. То же в форме товара (4.3).
- **Редактирование**: у живой заявки поля редактируются; у `LOCKED`-заявки форма read-only + баннер «Заявка заблокирована и защищена от редактирования», кнопка сохранения недоступна.
- Под «Сохранить запрос» у живой заявки — danger-кнопка «Удалить запрос» с Modal-подтверждением (аналогично «Удалить товар» в 4.3); после удаления — возврат к списку запросов. У read-only заявки кнопки нет.

### 4.5. Мои запросы

- Хедер: «Мои запросы» + `+`.
- Список карточек: миниатюра 56×56 отдаваемого товара (фото берётся из кеша `items` по `offeredItemId` — заявка его не отдаёт, см. `PROJECT.md` §4.3; при отсутствии — плейсхолдер) + две строки. Первая — название отдаваемого (одна строка с ellipsis) и StatusTag справа в той же строке (Активен/В процессе/Зарезервирован/Завершён/Выполняется), вторая — стрелка `→` и описание желаемого (не более двух строк). Подписи «Отдаю»/«Хочу» не используются — направление обмена читается по стрелке, смысл строк дублируется в `aria-label` карточки; тег статуса не выносится отдельной строкой, чтобы не увеличивать высоту карточки.
- Тап по карточке → список цепочек обмена (4.6). Редактирование запроса — кнопкой «Изменить запрос» в сводке на этой странице (4.6); для `LOCKED` — read-only. Удаления из списка нет: карточка — только навигация.
- Пустое состояние: «У вас нет запросов. Создайте новый» + CTA.
- Навигация: активный пункт «Запросы».

### 4.6. Список цепочек обмена (по конкретному запросу)

- Хедер: «Назад» + «Варианты обмена».
- Компактный блок сводки запроса (фон `bg-card`, radius-md, padding `--spacing-md`, без рамки): миниатюра отдаваемого товара 40×40 radius-sm, рядом две строки Body Small — «Отдаёте: [товар]» (`text-primary`) и «Получаете: [желаемый]» (`text-secondary`) + кнопка-иконка `text` (✎, без текста, aria-label «Редактировать запрос») — ведёт на форму редактирования 4.4. Кнопки правки в Penpot нет: это единственная точка входа в редактирование запроса, поэтому она сохранена.
- Список ChainCard (§2.7), сортировка по убыванию вероятности — на клиенте: бэкенд отдаёт цепочки по дате создания (`ORDER BY c.created_at DESC`).
- Действие карточки и приглушение недоступных вариантов — по матрице `PROJECT.md` §2.6, оформление — §2.7. На `PROPOSED`-карточке под мета-строкой — таймер дедлайна ответа, на `FROZEN`-карточке — «Осталось … на отправку»; на `CANDIDATE` таймера нет. При `FROZEN` над списком баннер «Сделка по одной из цепочек уже согласована. Остальные варианты недоступны.» и кнопка правки запроса `disabled`.
- Пустое состояние: «Пока нет подходящих цепочек. Попробуйте изменить запрос позже».

### 4.7. Детали цепочки

- Хедер: «Назад» + «Цепочка обмена».
- Полная схема (§2.8), вертикальная на моб., может быть горизонтальной с прокруткой на десктопе для длинных цепочек.
- На `CANDIDATE` действий на этом экране нет — отклик на кандидата получаемого звена выполняется на экране товара цепочки (§2.8) и на карточке списка (§2.7).
- Внизу экрана — «Посмотреть всю цепочку», затем действие второго раунда (§2.8; матрица — `PROJECT.md` §2.6). На `FROZEN`/`IN_PROGRESS` над кнопкой — плашка жёсткой блокировки, на `COMPLETED` её нет. На вакантной `PROPOSED` (непустой пул замен) над кнопкой — warning-плашка «Участник отказался. Выберите замену, чтобы продолжить обмен» и «Требуется действие» → экран замены. На `PROPOSED` между шапкой и «Описанием» — таймер дедлайна ответа (§2.7).
- Конфликт (`409`, например цепочка успела измениться) — тост с объяснением и перезагрузка карточки/списка.

**Экран замены участника** (`/chains/:chainId/replacement`):

- Вход — кнопка «Требуется действие» на карточке варианта (§2.7) и на деталях цепочки при непустом
  пуле замен (`PROJECT.md` §4.8); над кнопкой на деталях — warning-плашка «Участник отказался…».
- Карточка кандидата строится по образцу ChainCard (§2.7): крупное фото (пропорция 311:171, radius-md,
  без фото — заглушка с первой буквой названия), название (Subtitle), **полное** описание товара
  кандидата (Body, `text-secondary`, переносится, не режется), строка «Хочет: …» (Caption,
  `text-secondary`); внизу — пилюля актуальности («Актуальна»/«Давно не обновлялась», тон на 15%
  заливке) слева и radio выбора (22×22) справа. Карточка — единый label радио на всю ширину списка
  (тач-таргет ≥44×44), выбранная — рамка 2px `accent-primary`, фокус-ринг — на карточке при фокусе
  radio.
- Список кандидатов — вертикальный, gap 12, подгрузка клиентская по 10 («Показать ещё»); низ
  экрана — sticky-футер «Ни одна из замен не подходит» (`default`, 44px) / «Пригласить замену»
  (`primary`, 52px, `disabled` до выбора).
- Статусные экраны (ожидание ответа / замена подтверждена) — центрированная колонка: статус-иконка в
  круге 80×80, заголовок, описание; на «Замене подтверждена» — сводка новой цепочки (миниатюры
  28×28 по кольцу со стрелками, пилюля «Цепочка собрана», «N участников в цепочке»). Откат — EmptyState
  с пояснением и кнопкой перехода.

- Avatar (`lg`), имя, email.
- Тумблер темы.
- Статистика обменов: число завершённых цепочек.
- Навигация: активный пункт «Профиль».

**Смена пароля** (`/profile/password`):

### 4.9. Сделка: отправка и получение

Экраны жизненного цикла сделки после заморозки (макеты 4.9 «Сделка», нумерация Penpot разошлась с
этим документом — в Penpot профиль это 4.10). Вход — кнопка «Перейти к сделке»/«Требуется действие»
(§2.7/§2.8) на `/chains/:chainId/deal`; статусы отправки/получения — на
`/chains/:chainId/deal/shipments` и `/deal/receipts`. Шапка `ChainPageHeader` («Сделка» + «Назад» на
детали цепочки), глобального таб-бара нет (§2.12). Низ экрана — кнопка действия и `secondary` large
«Посмотреть детали цепочки»: на экранах отправки (ship/товары в пути/все доставлены) ведёт сразу в
статусы отправки (`/deal/shipments`), на экранах получения — в статусы получения
(`/deal/receipts`) — отдельной ссылки на статусы нет ни там, ни там, детали цепочки открываются
«Назад». На десктопе (1024px+) экран сделки не растягивается на всю высоту вьюпорта — кнопки идут
сразу за контентом, а не прижимаются к низу окна (макеты 4.9 только мобильные).

Ветка экрана — чистый дискриминант `dealState(chain)` из статуса цепочки и
`requestStatus` участников. «Отправил» = заявка уже не `LOCKED`, «я забрал» = заявка звена-источника
`DONE`. На `CANDIDATE`/`PROPOSED`/`BROKEN` сделки ещё нет — `/deal` редиректит на детали цепочки
(весь второй раунд живёт на 4.6/4.7/4.8).

| Состояние          | Условие                         | Экран                   |
| ------------------ | ------------------------------- | ----------------------- |
| `ship`             | моя заявка `LOCKED`             | «Отправка товара»       |
| `shipped-waiting`  | я отправил, отправили не все    | «Товары в пути»         |
| `in-transit`       | отправили все, я ещё не забрал  | «Ваш товар доставлен» |
| `received-waiting` | источник `DONE`, цепочка идёт   | «Вы подтвердили товар»  |
| `completed`        | `COMPLETED`                     | «Заберите свой товар»   |
| `unavailable`      | `CANDIDATE`/`PROPOSED`/`BROKEN` | редирект на детали      |

**Отправка товара** (макет «4.9 Сделка — Отправка товара»):

- Штрих-код отправки в начале экрана: подпись «Предъявите этот штрих-код при отправке», полоса
  вертикальных штрихов и цифровой код. Фиктивный — детерминированно генерируется из id цепочки,
  реального сканирования нет.
- Таймер «Осталось N ч M мин на отправку» (иконка-часы, тон `warning`, значение из `freezeDeadlineAt`;
  при истёкшем — «Срок отправки истёк» тоном `error`).
- Блок «Вы отправляете: [мой товар] → [получаемый]» (миниатюры 28×28).
- Зелёная строка «🔒 Мы сохраним ваш товар ›» → модалка «Ваш товар в безопасности» («Ваш товар в
  безопасности: товары не будут отправлены, пока все участники не принесли их»).
- «Что нужно сделать» — 3 шага из макета с названием товара.
- «Где будем получать?» — заголовок секции (тот же стиль, что «Что нужно сделать») и карточка ПВЗ:
  адрес из `localStorage` (`deal:pickup:<chainId>`, по умолчанию — первый из зашитого списка), кнопка
  «Изменить» открывает модалку с `Select` (список + «Другой адрес» с полем ввода; пустой адрес не
  сохраняется).
- Фото товара перед отправкой (обязательное, `*`): блок «Прикрепить фото» с иконкой загрузки
  (по размеру повторяет превью, пропорция 16:10) → файл ужимается до 512px по большей стороне и
  кладётся в `localStorage` (`deal:photo:<chainId>:<requestId>`); превью с центрированными
  «Заменить фото»/«Удалить». Без фото кнопка отправки `disabled` и подсказка «Прикрепите фото
  товара перед отправкой».
- Кнопка-заглушка «Я отправил товар» (`primary` large block) — в проде её дёргала бы интеграция с
  Авито, сейчас она вызывает `POST /integrations/avito/handoffs`; под ней подпись «Обычно это
  подтверждает пункт выдачи — в демо подтверждаете вы». Подтверждением отправки служит обязательное
  фото упаковки, `Modal.confirm` не показываем (операция идемпотентна, двойной клик гасится `isPending`).

**Товары в пути** («Ждём остальных», макет «4.9 Сделка — Товары в доставке»): 🚚 «Вы отправили
товар», «Ждём, пока остальные участники принесут свои товары», плашка «Отправлено N из M», зелёная
строка «🔒 Ваш товар в безопасности ›» (та же модалка, что на отправке — про безопасность отправки),
секция «Статус доставки» со строками
товаров (миниатюра, название, пилюля «Отправлен» `accent` / «Доставлено» `success` / «Ожидает
отправки» `warning` — без галочек, `›` → трекинг) и кнопка «Я забрал товар» `disabled` с подписью
«Дождитесь, пока отправитель принесёт товар».

**Ваш товар доставлен** (макет «4.9 Сделка — Товары доставлены»): зелёный блок (заливка тона 12%,
radius-md) с ✅ «Ваш товар доставлен» и «Ваш товар уже в пункте выдачи. Проверьте его в удобное
время» (перед ним — фиктивный штрих-код получения с подписью «Предъявите этот штрих-код при
получении», тот же, что и на отправке, но со своим seed), карточка ПВЗ, «Вы получите: [мой товар] →
[получаемый]», строка «Проблемы с товаром?
**Открыть спор**» и кнопка-заглушка «Товар устраивает» (`POST /chains/{id}/receipt`, доступна, пока
источник `IN_PROGRESS`; `Modal.confirm` не показываем). «Открыть спор» — модалка «Открыть спор?» с
выбором причины («Товар не тот», «Товар испорчен», «Другое»; кнопка «Открыть спор» недоступна, пока
причина не выбрана) → модалка «Жалоба отправлена» (🛠) → флаг `deal:dispute:<chainId>` в
`localStorage` и вместо ссылки строка «Жалоба на рассмотрении».

**Вы подтвердили товар**: 🎉 «Вы подтвердили товар», «Спасибо! Мы отметили, что товар вам подходит.
Обмен завершится, как только все участники подтвердят получение», ниже — «Забрать товар можно будет
после подтверждения всеми участниками» (сам забор — на экране завершённой сделки, где лежит
штрих-код); статусы получения открываются кнопкой «Посмотреть детали цепочки».

**Заберите свой товар** (завершённая сделка): 📦 «Заберите свой товар»,
«Обмен прошёл успешно» и «Получите свой товар в пункте выдачи», под ними — фиктивный
штрих-код получения (тот же, что на экране «Ваш товар доставлен»), кнопка «К моим запросам».

**Статусы отправки/получения** (макеты «4.9 Сделка — Статусы отправки/получения»): один список
`ParticipantStatusList` с mode. Строка: аватар + псевдоним-животное по позиции (§2.9; для себя —
«Вы»/«Я») + пилюля справа, ниже «отдаёт → получает». Своя строка — рамка 2px `accent-primary`, как
на схеме 4.8. Пилюли: `shipments` — `LOCKED` → warning «Ожидает отправки», иначе success «Отправлено»;
`receipts` — источник `DONE` → success «Получил», иначе warning «Ожидаем». Подпись текстом обязательна
(§1.8), глифы-галочки в пилюлях не рисуются.

**Трекинг** (модалка «4.9 Модальное окно — Трекинг»): фиксированный список этапов без дат — времени
API не отдаёт, выдуманные даты хуже, чем их отсутствие. «Пройденность» по
`requestStatus`: `LOCKED` — ничего и подпись «Отправитель ещё не принёс товар», `IN_PROGRESS` — до
«Доставлено в пункт выдачи» включительно, `DONE` — ещё и «Получено». Последний пройденный этап —
жирный с акцентной точкой, пройденные — `status-success`, непройденные — серые.

**Модалки** — все через `App.useApp().modal` (§2.11): «Ваш товар в безопасности» (одинаковая на всех
экранах сделки — про безопасность отправки), «Жалоба отправлена» (🛠), выбор причины
спора («Товар не тот», «Товар испорчен», «Другое»), выбор ПВЗ (без
закрытия по маске). Подтверждающих `Modal.confirm` для кнопок-заглушек нет: отправка подтверждается
фото упаковки, получение — самой операцией (обе ручки идемпотентны, повторный клик гасится `isPending`).

**Имитации** (бэкенда под ними нет, в коде помечаются комментарием со словом «имитация»):
адрес ПВЗ, фото упаковки, штрих-коды отправки/получения, трекинг, спор. Время событий и
«ориентировочную дату получения» не показываем — API их не отдаёт.

## 5. Состояния и особые случаи (сквозные, применимы ко всем экранам списков/форм)

| Ситуация                                       | Поведение                                                                                           |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Загрузка списка/карточек                       | Skeleton, повторяющий целевую разметку                                                              |

| Товар не активен («Зарезервирован»/«В архиве») | Недоступен для выбора в новом запросе, визуально приглушён + подпись                                |

## 6. Критерии готовности к разработке

- [ ] Токены (§1) заведены как CSS custom properties / theme-объект, переключение темы — атрибутом на корне.
- [ ] Компоненты (§2) реализованы со всеми состояниями (`default/hover/active/focus/disabled/loading`), без исключений для интерактивных элементов.
- [ ] Все 8 экранов (§4, включая авторизацию) свёрстаны на 375/768/1024 из одной адаптивной разметки (не 3 отдельных макета).
- [ ] Все состояния из §5 покрыты для каждого списка/формы.
- [ ] Контраст и минимальный тач-таргет (44×44px) проверены на обеих темах.
- [ ] Ни одно состояние (успех/ошибка/предупреждение/вероятность) не передаётся только цветом.
